# 主从槽位隔离架构设计方案

> 版本：v1.0
> 日期：2026-09-05
> 状态：已批准，实施中

## 一、背景与目标

### 1.1 问题

单槽模式下，主 agent 和子 agent 同权挂起排队，一旦主 agent 被驱逐或超时，整个任务失败。多槽模式下，如果不做隔离，子 agent 可能占用主 agent 的槽位，导致主 agent 请求被驱逐，来回切换开销大。

### 1.2 目标

- **故障域隔离**：主 agent 独占预留槽位，子 agent 失败不影响主 agent
- **优先级保障**：主 agent 槽位不被子 agent 抢占
- **资源优化**：子代理自动关闭强占、不持久化 KV，省显存
- **效率优化**：子代理更短超时、更少重试，失败后主 agent 快速重新调度
- **向后兼容**：单槽模式、旧配置不受影响

## 二、身份识别层（已完成 v2.29）

### 2.1 识别规则

| 请求特征 | 身份 | 说明 |
|---|---|---|
| 带 `AGENT_TAG::SUB` 标记 | `secondary`（子代理） | Trae 全局规则注入，主 agent 调用 Task 时在 query 首行插入 |
| 无标记 / 带 `AGENT_TAG::MAIN` | `primary`（主代理） | 默认身份 |
| 非推理请求（/tokenize、/models 等） | 不识别 | 走现有逻辑 |
| 识别失败（JSON 解析错误等） | 回退 `primary` | 走现有逻辑 |

### 2.2 标记协议

```
AGENT_TAG::SUB::<8位随机任务ID>
```

- 独占一行，标记后空一行再写内容
- 主 agent 调用 Task 工具时，在 query 参数首行插入
- 该 query 即子 agent 的第一条 user 消息，因此标记确定性地出现在子 agent 请求体中

### 2.3 标记剥离

- 网关识别到标记后，从 messages 中剥离标记行
- 转发给后端的请求体中无 `AGENT_TAG` 残留，不污染模型上下文
- 剥离后注入 Header：`X-Agent-Role: sub` / `X-Agent-Role: main`

### 2.4 指纹兜底（P4，可选）

如果模型偶尔忘记打标记（规则执行率不是 100%），用启发式指纹补判（只记录告警，不影响主流程）：

- tools 数量 < 10 且无 Task 工具 → 可能是子代理
- system prompt 长度 < 500 token → 可能是子代理
- 日志告警：`[AGENT-TAG][WARN] 疑似子代理但无标记，按主代理处理`

## 三、槽位分配层（P1，核心新增）

### 3.1 单槽模式（`--parallel 1`）

| 身份 | 槽位 | 强占 | 说明 |
|---|---|---|---|
| primary | slot 0 | 用户配置 | 保持现有行为 |
| secondary | slot 0 | **强制关闭** | 子代理任务完成后立即释放槽位，不占用主代理资源 |

**关键**：单槽模式下，子代理自动关闭强占（`preempt=false`），任务完成后立即释放，避免子代理占用 slot 0 导致主代理请求被驱逐。

### 3.2 多槽模式（`--parallel >= 2`）

| 身份 | 优先槽位 | 强占 | 驱逐策略 |
|---|---|---|---|
| primary | **slot 0（预留）** | 用户配置 | slot 0 标记为 `reserved`，子代理**禁止占用**；是否被 LRU 驱逐由用户强占配置决定 |
| secondary | slot 1 ~ slot N | **强制关闭** | 可被 LRU 驱逐，任务完成后立即释放 |

### 3.3 槽位选择优先级（子代理）

1. 优先选空闲槽位（slot 1 ~ N）
2. 多个空闲时，按 LCP 相似度选（KV 复用优先）
3. 无空闲时，按 LRU 选最旧的槽位驱逐
4. **绝对禁止选 slot 0**（即使 slot 0 空闲）

### 3.4 边界情况

| 场景 | 处理 |
|---|---|
| 所有非 slot 0 都忙 | 子代理排队等待，不抢占 slot 0 |
| 主代理不在 slot 0（异常） | 子代理仍不选 slot 0，选其他槽位 |
| 只有 2 个槽位，多个子代理并发 | 子代理在 slot 1 排队，主代理独占 slot 0 |
| 主代理请求到达时 slot 0 被占用 | 正常驱逐（slot 0 是主代理预留，子代理不会占用） |

## 四、差异化配置层（P2）

子代理自动应用以下配置（覆盖用户全局配置）：

| 配置项 | 主代理 | 子代理 | 说明 |
|---|---|---|---|
| 强占（preempt） | 用户配置 | **false** | 子代理不占用槽位，任务完成立即释放 |
| KV 持久化 | 用户配置 | **false** | 子代理任务短，不需要恢复，省显存 |
| 首字节超时 | 120s（默认） | **60s** | 子代理任务简单，超时更快失败，主代理重新调度 |
| 重试次数 | 3 次（指数退避） | **1 次** | 子代理失败无所谓，主代理会重新调度 |
| 上下文预算 | 用户配置 | **减半**（可选） | 子代理任务短，用更短的上下文省显存 |
| TokenGuard 预算 | 用户配置 | **独立计算** | 子代理用更小的预算，避免挤占主代理 |

### 4.1 配置项

```json
{
  "SlotMode": "DualPrimarySecondary",
  "PrimarySlotIndex": 0,
  "SecondaryAutoDisablePreempt": true,
  "SecondaryKvPersist": false,
  "SecondaryTimeoutSeconds": 60,
  "SecondaryRetryCount": 1
}
```

| 配置项 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `SlotMode` | enum | `Single` | `Single` = 关闭主从隔离；`DualPrimarySecondary` = 开启主从隔离 |
| `PrimarySlotIndex` | int | `0` | 主代理预留槽位索引 |
| `SecondaryAutoDisablePreempt` | bool | `true` | 子代理自动关闭强占 |
| `SecondaryKvPersist` | bool | `false` | 子代理是否持久化 KV |
| `SecondaryTimeoutSeconds` | int | `60` | 子代理首字节超时（秒） |
| `SecondaryRetryCount` | int | `1` | 子代理重试次数 |

## 六、崩溃恢复层

| 身份 | 恢复策略 |
|---|---|
| primary | KV 持久化开启 → 崩溃后恢复 slot 0 的 KV，继续任务 |
| secondary | KV 持久化关闭 → 崩溃后不恢复，任务失败，主代理重新调度 |

**关键**：子代理不持久化 KV，崩溃恢复时只恢复主代理的 slot 0，子代理的槽位直接清空，省恢复时间。

## 九、关键设计决策

### 9.1 为什么 slot 0 是硬预留而不是软优先？

子代理即使 slot 0 空闲也不能用，否则主代理请求来了发现 slot 0 被子代理占了，又要驱逐子代理，来回切换开销大。硬预留保证主代理永远有 slot 0 可用。

### 9.2 为什么子代理 KV 不持久化？

4 个子代理并发，如果每个都持久化 KV，显存很快爆；子代理任务短（几十秒），不需要恢复，不持久化省大量显存。

### 9.3 为什么子代理超时更短？

子代理卡住 60s 就失败，主代理立即重新调度，不用等 120s；子代理失败成本低（主代理会重试），但卡住成本高（占用槽位）。

### 9.4 为什么崩溃恢复只恢复主代理？

子代理不持久化 KV，崩溃后直接清空，省恢复时间；主代理的 slot 0 KV 恢复后继续任务，子代理由主代理重新调度。
