# LlamaHarness 可观测体系设计方案（v2.22）

- 版本：v2.22（2026-09-01，方案设计稿）
- 定位：从「能跑 / 跑得快」进化到「可以复盘、定位慢在哪里」——**统一统计口径 → 指标持久化 → 面向事后性能分析**三件事闭环。
- 基础：v2.21 性能监控模块（PerfPoint / PerfSampler / RequestTiming / PerfLog / PerfAnalyzer / PerfMonitorView，173 测试全绿）为本次演进的地基。
- 实施分支：`refactor/mainform`；每步独立 build + test + commit（项目固定流程）。

---

## 1. 目标与演进定位

| 阶段 | 状态 | 能力 |
| ---- | ---- | ---- |
| 能跑 | ✅ 已具备 | 功能闭环：KV 缓存 / 调度 / 故障自愈 |
| 跑得快 | ✅ 已具备 | v2.21 性能监控：时延四段 / 系统资源 / 吞吐采样 / 阈值告警 |
| 可复盘 | ⬜ **本方案** | 统一统计口径 + 指标持久化 + 事后回溯分析 |

**本方案要回答的三个事后问题**：
1. 什么时候变差？（趋势 + 会话对比）
2. 为什么变差？（归因：prefill 慢了 / KV 命中率下降 / 调度开销上涨 / 日志丢弃加剧）
3. 跨会话、跨版本能不能直接对比？（统一口径 + 持久化，不再人肉 grep）

## 2. 现状盘点（v2.21 基线 vs 缺口）

| 指标层 | 已有能力 | 缺口 |
| ---- | ---- | ---- |
| ⑤ 网关时延 | ✅ RequestTiming 四段（wake/gateway/backend/total）+ 最近 200 环形 + 会话聚合 + perf.log `timing` 行 | — |
| ⑥ 系统资源 | ✅ PerfPoint（cpu/mem/vram/inflight）1s 采样 + perf.log `system` 行 | — |
| ③ llama-server 推理 | ⚠️ PerfPoint 已采 pp_tps/tg_tps/tokens_cached/ctx（`cpp` 行） | 命名未与业务口径统一（pp_tps vs prompt_eval_tps）；draft_accept_rate 未采集 |
| ① KV 缓存 | ⚠️ RestoreStats 内存计数（`_totalHits/_totalFalseMiss/_totalFalseHit/_totalAttempts`）；save/restore 有 Stopwatch 但只打日志 | **未接入 perf 体系、未持久化**；hit/miss 口径未写死 |
| ② 调度器 | ⚠️ GetSlot 排队有 Stopwatch、TryAllocateLocked 返回 evicted、wakeup 有 wakeStart 计时 | **未接入 perf 体系、未持久化** |
| ④ 日志管道 | ⚠️ LogPipeline 有 `_dropped`（TakeDroppedDelta）+ io_fail，[LOG-PIPE] 埋点 | **未进 perf 体系**；flush 耗时未计时 |

**核心差距一句话**：KV / 调度 / 日志管道三类指标「有内存、有日志、无统一模型、无持久化、无口径文档」——正是进程重启丢失、跨会话不可比、无法归因的根源。

## 3. 指标分层注册表（统一口径的唯一权威）

> **设计原则**：本表是每个指标**口径 / 单位 / 触发条件 / 持久化**的唯一权威来源；代码侧落一个 `MetricKeys` 常量类（键名与下表一一对应），任何新增/修改指标必须同时改注册表和 MetricKeys，禁止各处随意变体命名。

### ① KV 缓存指标（会话维度）

| 指标键 | 口径定义 | 单位 | 触发条件 | 数据来源 | 持久化 |
| ---- | ---- | ---- | ---- | ---- | ---- |
| `kv_hit_delta` | 前缀指纹命中（含 HitByDelta）的累计次数 | count | restore 判定命中时 +1 | RestoreStats._totalHits | ✅ perf.log（周期快照） |
| `kv_false_miss` | 非预期 miss：前缀无变更却 miss（区分：真实前缀变更属正常 MISS，不计入） | count | false_miss 判定时 +1 | RestoreStats._totalFalseMiss | ✅ perf.log（周期快照） |
| `kv_restore_ms` | 单次 eager/lazy restore 耗时（Stopwatch ticks） | ms | 每次 restore 完成 | 埋点处计时 | ✅ perf.log（事件行） |
| `kv_save_ms` | 单次保存耗时（首请求存档 / 休眠快照 / 条件式后台 save） | ms | 每次 save 完成 | 埋点处计时 | ✅ perf.log（事件行） |
| `saved_n` | 该会话最大 token 偏移量 | token | 每次 save 后取最大值 | RestoreStats.SavedN | ✅ perf.log（周期快照） |

**口径约束**：hit/miss 严格区分——真实前缀变更属于正常 MISS，**不计入 false_miss**；`kv_hit_delta` 只计 HitByDelta 与真实命中，`kv_false_miss` 只计前缀未变却 miss 的异常。

### ② 调度器指标（全局 + 槽维度）

| 指标键 | 口径定义 | 单位 | 触发条件 | 数据来源 | 持久化 |
| ---- | ---- | ---- | ---- | ---- | ---- |
| `slot_select_ms` | 槽路由选择总耗时（GetSlot 从进入排队到分配完成，含排队等待） | ms | 每次 GetSlot 完成 | SlotAffinity.GetSlot Stopwatch | ✅ perf.log（事件行） |
| `evict_count` | 驱逐事件累计次数（含抢占驱逐 / LRU 淘汰 / 手动） | count | 每次驱逐发生时 +1 | SlotAffinity.TryAllocateLocked evicted 非空 | ✅ perf.log（周期快照增量） |
| `wakeup_total_ms` | 服务完整唤醒耗时（Standby→Running，模型加载 + eager restore + 预热） | ms | 每次唤醒完成 | SmartScheduler.WakeUpAsync elapsed | ✅ perf.log（事件行） |
| `preempt_trigger` | 强占触发累计次数（autoPre 抢占锁槽） | count | 每次 autoPre 生效时 +1 | SlotAffinity 强占路径 | ✅ perf.log（周期快照增量） |

### ③ llama-server 推理指标（task 维度）

| 指标键 | 口径定义 | 单位 | 触发条件 | 数据来源 | 持久化 |
| ---- | ---- | ---- | ---- | ---- | ---- |
| `prompt_eval_tps` | prefill 吞吐（= 现有 pp_tps，统一命名） | tok/s | 5s 慢采样 | PerfPoint.PpTps / /slots | ✅ 已有 |
| `gen_tps` | 生成 token 吞吐（= 现有 tg_tps，统一命名） | tok/s | 5s 慢采样 | PerfPoint.TgTps / /slots | ✅ 已有 |
| `draft_accept_rate` | 投机解码接受率 | ratio 0~1 | llama.cpp 暴露时采集 | /metrics 投机计数（**条件采集，见 §8**） | ⚠️ 待核实 |

### ④ 日志管道指标（全局）

| 指标键 | 口径定义 | 单位 | 触发条件 | 数据来源 | 持久化 |
| ---- | ---- | ---- | ---- | ---- | ---- |
| `log_dropped_lines` | 队列丢弃累计行数 | count | 队列满丢弃时累计 | LogPipeline._dropped | ✅ perf.log（周期快照增量） |
| `log_flush_cost_ms` | flush 单次耗时 | ms | 每次 Flush 完成 | LogPipeline 写线程计时 | ✅ perf.log（周期快照均值） |

### ⑤ 网关层性能指标（v2.21 已实现，本方案回归基线）

| 指标键 | 口径定义 | 单位 | 数据来源 | 持久化 |
| ---- | ---- | ---- | ---- | ---- |
| `wake_wait_ms` | 唤醒/排队等待时延 | ms | RequestTiming.WakeWaitMs | ✅ timing 行 |
| `gateway_ms` | 网关预处理时延 | ms | RequestTiming.GatewayMs | ✅ timing 行 |
| `backend_ms` | 后端推理 + SSE 转发时延 | ms | RequestTiming.BackendMs | ✅ timing 行 |
| `total_ms` | 请求总时延 | ms | RequestTiming.TotalMs | ✅ timing 行 |
| `req_inflight` | 在途请求数 | count | PerfPoint.Inflight | ✅ system 行 |

### ⑥ 系统资源采样指标（v2.21 已实现，回归基线）

| 指标键 | 口径定义 | 单位 | 数据来源 | 持久化 |
| ---- | ---- | ---- | ---- | ---- |
| `cpu` | CPU 使用率 | % | PerfPoint.CpuPercent | ✅ system 行 |
| `mem` / `mem_total` | 内存使用 / 总量 | GB | PerfPoint.MemUsedGb/MemTotalGb | ✅ system 行 |
| `vram` / `vram_total` | 显存使用 / 总量 | MB | PerfPoint.VramUsedMb/VramTotalMb | ✅ system 行 |

## 4. 统一指标模型扩展

**核心设计决策：按「事件型 / 累积型 / 周期型」三形态接入，不强行塞进一种模型。**

| 形态 | 特点 | 适用指标 | 接入方式 |
| ---- | ---- | ---- | ---- |
| **事件型**（单次瞬时值） | 有请求/动作才发生，需精确时刻 | kv_restore_ms / kv_save_ms / slot_select_ms / wakeup_total_ms | 仿 RequestTiming 新增事件流 + perf.log 事件行 |
| **累积型**（单调计数器） | 会话内累计，需看增量 | kv_hit_delta / kv_false_miss / evict_count / preempt_trigger / log_dropped_lines | PerfPoint 扩展可空字段，采样时读源快照（增量 = 相邻点差） |
| **周期型**（采样点） | 按固定节奏取值 | cpu / mem / vram / pp_tps / tg_tps / inflight | 已有 PerfPoint 体系 |

- **事件型**：新增 `PerfEventTracker`（泛化 RequestTimingTracker：Begin→Complete 打点 + 最近 N 环形 + Completed 事件），perf.log 新增 `event` 类行。
- **累积型**：PerfPoint 增加可空字段 `KvHitDelta / KvFalseMiss / EvictCount / PreemptTrigger / LogDroppedLines`，由 PerfSampler 在 1s tick 时从 RestoreStats / SlotAffinity / LogPipeline 读快照；趋势图与告警直接复用 PerfAnalyzer.ValueOf（指标键 = 注册表键）。

## 5. 持久化设计（perf.log v2）

在 v2.21 perf.log 基础上扩展，**统一格式协议不变**（每行 `Kind,ts,key=value,...`），仅增加行类型与会话边界：

| Kind | 内容 | 示例 |
| ---- | ---- | ---- |
| `system` | 1s 周期：系统资源 + inflight | `system,ts,cpu=3.2,mem=28.5,total=64.0,vram=1234,vram_total=8192,inflight=0` |
| `cpp` | 5s 周期：推理吞吐（仅 cpp 字段非空时写） | `cpp,ts,pp_tps=..,tg_tps=..,tok=..,ctx=0.180,slots=..` |
| `timing` | 请求级：网关四段时延（v2.21 已有） | `timing,ts,app=..,path=..,success=1,wake=..,gateway=..,backend=..,total=..` |
| `kv` | 事件型：save/restore 耗时 | `kv,ts,op=restore,key=..,slot=2,ms=1253,saved=..` |
| `sched` | 事件型：槽选择 / 唤醒耗时 | `sched,ts,op=wakeup,ms=8120` / `sched,ts,op=slot_select,ms=3` |
| `count` | 累积型周期快照（KV/调度/日志管道计数增量） | `count,ts,kv_hit_delta=12,kv_false_miss=1,evict=3,preempt=0,log_dropped=0,flush_cost_avg=2.1` |
| `session` | 会话边界标记（跨会话对比锚点） | `session,ts,sid=uuid,app=LlamaHarness,ver=2.22` |

**关键新增——会话边界 `session` 行**：
- 启动时写一行（含 `sid` UUID + 版本号），关闭时写一行 `session,ts,op=end,sid=..`
- 离线分析按 sid 分组 → **跨会话、跨版本直接对比**（无需人肉 grep）
- 版本号进 sid 上下文，支持「升级后该指标是否退化」的版本对比

轮切策略（5MB×3）与独立直写通道沿用 v2.21，**不回归主日志队列**。

## 6. 面向事后分析（PerfAnalyzer v2）

在 v2.21 双源共享内核上扩展三块能力：

### 6.1 会话摘要扩展（实时 + 离线共用）
```
kv_hit_rate       = kv_hit_delta / (kv_hit_delta + kv_false_miss + 正常miss)   # KV 命中率
kv_false_miss_rate= kv_false_miss / 总 miss 数                                  # 异常 miss 占比
avg_slot_select_ms / p50 / p95 / max                                            # 调度耗时分布
avg_restore_ms / avg_save_ms                                                    # KV 存取耗时
wakeup_total_ms 序列                                                            # 唤醒耗时趋势
log_dropped_rate = log_dropped_lines / 总日志行数                                # 日志丢弃率
```

### 6.2 跨会话 / 跨版本对比（读 perf.log 多段）
- 按 `session` 行切分多个会话段
- 同指标跨会话聚合：`avg(metric) by session` → 趋势表 / 对比视图
- 同版本内多会话基线 → 定位「这次会话特别慢」的会话
- 版本字段 → 定位「升级后变慢」的版本

### 6.3 退化归因（回答「为什么变差」）
```
若 gen_tps 下滑：
  ├─ prompt_eval_tps 下滑？      → prefill 变慢（模型/输入变化）
  ├─ kv_hit_rate 下滑？          → KV 命中下降（前缀变化/缓存失效）
  ├─ kv_restore_ms 上涨？        → restore 变慢（快照变大/磁盘）
  ├─ slot_select_ms 上涨？       → 调度争抢加剧（并发/强占）
  ├─ log_dropped_lines 上涨？    → 日志队列打满（写入瓶颈）
  └─ 系统层：cpu/vram 压力上涨？ → 资源瓶颈
```

## 8. 边界与取舍

- **draft_accept_rate（投机解码）**：llama.cpp `/metrics` 是否稳定暴露投机计数**待核实**——若后端未开启 `--draft` 或端点无该字段，方案降级为「条件采集」（探测到才写），不阻塞主链路。
- **不引入数据库**：持久化延续 perf.log 文件 + 分析内核，**零第三方依赖**（与项目既定取舍一致）；跨会话查询是「按 session 切分多段」而非 OLAP 库。
- **不记录请求体 / 业务 payload**：与 request_dump 语义严格区分，隐私敏感。
- **累积型指标的口径**：存量会话重启后计数器归零（本方案接受——跨会话对比依赖 session 边界，不依赖绝对计数），增量语义（相邻采样点差）保证趋势正确。
- **埋点开销**：事件型埋点全部 Stopwatch ticks + 常量级内存，不进请求热路径的序列化；perf.log 独立直写通道不受影响。

## 9. 验收标准

1. 指标键全量在注册表有定义，MetricKeys 与注册表一一对应（自动测试校验）。
2. 六层指标全部接入 perf 体系，perf.log 可完整重建一个会话的关键性能画像。
3. 跨会话：读取多段 perf.log 能按 sid 分组对比（至少 KV 命中率 / 吞吐 / 调度耗时三组）。
4. 归因：给定一个「gen_tps 下滑」场景，分析输出能区分 prefill / KV / 调度 / 日志 / 资源五类根因。
5. 每步 build 0 错误 + 测试全绿（基线 173，预计新增 15~25 项）。
