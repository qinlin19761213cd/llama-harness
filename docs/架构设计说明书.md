## 1. 项目概述

### 1.1 定位

LlamaHarness 是一个 Windows 桌面应用，为本地 llama.cpp 的 llama-server（OpenAI 兼容 LLM API 服务）提供：

1. **图形化启动器**：选模型、调参数、一键启停，实时日志；
2. **智能按需调度器**：常驻监听前端端口（默认 8080），首个推理请求触发唤醒，闲置 15 分钟自动休眠释放显存——"用即满血、闲即释放"；
3. **P 核亲和性管理**：Intel 混合架构 CPU（i5-13900F）上把 llama-server 绑定纯 P 核并自愈重绑；
4. **实时推理统计**：解析进程日志 print_timing 块，按请求展示输入/输出速度、投机解码命中率、f_sim_best、总耗时；
5. **KV 缓存复用**（v2.0/v2.3）：单槽/多槽均激活——按应用指纹固定槽位（n_slots 路由防跨槽漂移），驱逐/重启/截断/崩溃四个场景的 KV 快照 save/restore，主力会话自动冻结防驱逐，Tool 链会话锁定，前缀 HIT/MISS 可观测；
6. **思考模式拦截**（v2.0/v2.3）：启动参数 `--reasoning on/off` 决定初始档位；代理层识别"开启/关闭思考模式"及三档推理指令切换状态机；对请求中客户端自带的 `chat_template_kwargs`（reasoning_effort / enable_thinking）**统一清洗**后按状态机重新注入，全局状态机跨请求保持；
7. **TokenGuard + 输出续接**（v2.0）：真实分词计数防上下文超长 400，轮次制裁剪；finish_reason=length 自动续接（客户端无感），截断断点快照驻留；
8. **bad_alloc 崩溃自动恢复**（v2.0）：任务级内存耗尽时双源检测 → 三分支恢复（存活→KV 快照接续 / 进程死→重启重放 / 客户端断→不重放），SSE keep-alive 保活客户端无感续接，熔断器防无限循环。

### 1.2 技术选型

| 维度   | 选择                                 | 理由                                   |
| ------ | ------------------------------------ | -------------------------------------- |
| 运行时 | .NET 8（net8.0-windows）             | 目标框架，Windows 桌面                 |
| UI     | WinForms                             | 功能边界小，避免 WPF/AvalonUI 过度设计 |
| 依赖   | **零第三方 NuGet 包**                | 单项目自包含，降低供应链与维护成本     |
| HTTP   | System.Net.HttpListener + HttpClient | BCL 内置，监听本机回环无需管理员权限   |
| 配置   | System.Text.Json                     | BCL 内置                               |

### 1.3 部署形态

- 单 exe（Llama-harness.exe），运行时生成：
  - **config/** 目录（首次保存时自动创建）：
    - config.json —— 用户配置（含本机模型/exe 路径，不入库）；
    - slot_bindings.json —— 槽位亲和绑定表（key→slot/强占/KV缓存开关，持久化）；
    - kv_cache_index.json —— KV 快照索引（key→slot/savedAt/nTokens/size）；
  - **logs/** 目录（首次写入时自动创建）：
    - harness.log / harness.log.1 —— 主日志（2MB 轮切）；
    - warn_error.log —— 警告/错误独立日志（5MB 轮切，带上下文）；

**阶段状态机**：

```text
Standby ──推理请求/LaunchNowAsync──▶ Waking ──WaitReady ok──▶ Warming ──预热完成──▶ Running
   ▲                                    │                        │                    │
   │                          WaitReady fail        （eager restore + dummy 预热      │ 闲置超时（10s 观察期+KV save）
   └────────────────────────────────────┘          ≤60s，失败不阻塞）                ▼
                    ▲                                     Sleeping（释放过渡）
                    │  Kill 完成（Exited 回调）                  │
                    └───────────────────────────────────────────┘
```

- **Standby** 是待机稳态：探测类请求 503（无唤醒权），推理请求触发唤醒；
- **Warming** 是就绪后、Running 前的预热子状态：eager restore（autoPre key 有快照者立即恢复 KV）+ dummy 预热（max_tokens=1 直连后端捕获 decode graph）；期间到达的请求经 `EnsureRunningAsync` await `_wakeTask` 天然排队等待，不触发全量 prefill；整体 60s 超时兜底，失败不阻塞转 Running（首请求仍有惰性 restore 自愈）；
- **Sleeping** 是休眠释放过渡态：一切请求（含推理）直接 502，进程退出后经 Exited 回调回 Standby；
- **StopNow**（手动停止）直接 Standby，不经过 Sleeping。

**AcceptLoop 与请求分类**：

- `HttpListener` 双前缀常驻监听（`http://localhost:8080/` + `http://127.0.0.1:8080/`）；
- C-008：accept loop 运行期异常重试（连续 3 次失败 → RaiseStatus "监听失败"）；
- `HandleRequestAsync` 分类处理：
  - `GET /__status__` → JSON 状态（见 §6.1，不触发唤醒、不刷新闲置计时）；
  - Sleeping（释放过渡）收到任何请求 → 502「正在休眠释放，请稍后重试」；
  - Standby 下探测类请求（无唤醒权，如健康检查）→ 503；
  - 推理请求 → inflight++（`_inflightPeak` 记录峰值，C-102）→ 必要时 WakeUp → ForwardAsync；
  - try/finally 保证 inflight--（C-002）。

**唤醒流程**（`WakeUpAsync`）：

1. `StatsReset?.Invoke()`（C-007：唤醒前清空旧轮统计，防跨轮污染）；
2. 唤醒计数 / 耗时统计（C-102）；
3. `LlamaFinder.BuildArgs` 拼接命令行；
4. `LlamaServerProcess.Start` 静默拉起；
5. `WaitReadyAsync`：探测后端端口（前端端口 +1 起），C-003 校验响应 body 含 `"object":"list"`（防其他服务误判就绪），进度日志 10s 首拍、之后每 15s；
6. SlotAffinity / KvCacheManager / RestoreStats 实例在 WaitReady 前创建（幂等），并清空 `_servedKeysThisRun` + `_savedKeysThisRun`（新进程槽位 KV 全空 → 唤醒后各 key 首次请求触发 restore 自愈，autoPre key 重新触发首请求存档）；
7. **Warming 预热**（`RunWarmingAsync`，整体 60s 超时兜底）：① eager restore——绑定表中 `KvCache=true && IsAutoPreKey && HasCache` 的 key 立即 `RestoreAsync`（单 key 30s WhenAny 守卫，成功记入 `_servedKeysThisRun` 防首请求重复 restore）；② dummy 预热——选第一个未绑定 KV 快照的槽位发 max_tokens=1 请求（直连后端端口绕过代理管道，捕获 CUDA graph / decode 路径；全绑定时跳过防污染已恢复 KV）；预热期进程崩溃则中止唤醒走失败清理（不带死进程进 Running）；
8. 唤醒计数在成功后累加。

**ForwardAsync 全管道**（`PrepareGatewayAsync`，顺序执行；E-1/E-3 单 DOM 管道：入口一次 `JsonNode.Parse`，①~⑤ 全程复用同一棵 `JsonObject`，末端只序列化 + 编码各一次；非法 JSON → root=null → 跳过全部 DOM 改写原样透传）：

```text
客户端请求
  │
  ├─① 思考模式拦截："开启/关闭思考模式"或推理档位指令 → 状态机迁移 + 剥离指令并改写消息，照常转发后端由模型生成确认
  │
  ├─② 槽位亲和：GetSlot(req.Headers, autoPreemptive)
  │     └─ Tool 链锁定：末条消息 role=tool → SetPreemptive(true) [KV-LOCK]；
  │        只解锁自己锁的键（_toolLockedKeys）[KV-UNLOCK]
  │
  ├─③ restore：槽位 KV 自愈——① isNew 重绑定（旧槽快照加载到新槽）或 ② 进程重启后该 key 首次使用（休眠唤醒自愈）
  │     → [KV-RESTORE] + 前缀哈希基线重置；本进程已服务过的 key 不再 restore（防旧快照回退内存新状态）
  │
  ├─④ TokenGuard.GuardAsync：真实分词计数，超长轮次二分裁剪（防 400）
  │
  ├─⑤ LogPrefixHash：轻量指纹(消息条数+各条 role|content长度) → [KV-HIT]/[KV-MISS]
  │
  ├─⑥ OutputContinuer.HandleStreamAsync：SSE 管道 + 截断续接（onTrunc 闭包 → save 断点快照）
  │
  ├─⑦ TryCrashRecoverAsync：bad_alloc 检测 → 三分支恢复
  │
  ├─⑧ §6.3 清理：completed && wasPending → DeleteCache + [KV-CLEANUP]
  │
  └─⑨ 首请求存档（1.1）：completed && IsAutoPreKey → 立即 SaveAsync 落盘快照（_savedKeysThisRun 每唤醒周期一次，防进程崩溃未休眠时磁盘快照停留旧状态；失败不阻塞主流程，下请求重试）
```

**强制流式**（`EnsureStreamTrue`）：C-005 DOM 优先解析 + 字符串降级替换，失败时透传原请求（仅 ForceStream=true 时执行）。

**其他健壮性行为**（代码已实现，备忘）：

- 后端端口自动探测：首选端口起向上 +1 上探至 +32（探测与实际绑定间存在 TOCTOU 窗口，属可接受风险）；
- 转发连接异常：500ms 后以全新请求重试一次；
- 崩溃双判据：5xx 响应体含 "bad allocation" 且 60s 内日志出现过 bad_alloc（`WasBadAlloc` 佐证窗口）；
- 线程数超出 P 核掩码核数时自动钳制（防超订降速）；
- 思考参数统一清洗：网关层移除客户端自带的 reasoning_effort / enable_thinking，按状态机重新注入（不信任客户端自行携带的值）；
- 崩溃恢复分支 B（进程死亡重放）在统一预算基础上再收紧 25%；
- 非流式推理请求每会话一次告警（提示流式体验更佳）。

**闲置休眠**（`SleepNow` → `SleepNowCoreAsync`）：闲置定时器（IdleMinutes，默认 15min）且 inflight==0 触发 → **10 秒静默观察期**（新请求/在途任务即取消休眠）→ `SaveAllSlotsBeforeStopAsync` 逐槽 save KV 快照（仅 KvCache=true 绑定，整体 60s 超时保底）→ Kill 进程树；休眠计数统计（C-102）；`VerifyVramReleasedAsync`（C-006：3s 后查显存，未回落则告警）。

**P 核自愈**：唤醒后及周期性 `CpuAffinity.Heal` 重绑 P 核掩码（防 E 核漂移）。

**思考模式状态机**：

- `ThinkingLevel {Off / Low / Medium / XHigh}`；
- `DetermineInitialThinkingMode(extraArgs)`：`--reasoning on`→XHigh / `--reasoning off` 或无参数→Off（默认不思考）；
- `InjectThinkingMode(json, ref level, out effortFix)`：三步处理——① 指令识别（"开启/关闭思考模式"等中文指令切换档位 + 剥离文本）；② **统一清洗**（移除客户端自带的 `chat_template_kwargs.reasoning_effort` / `enable_thinking`）；③ 按状态机注入（**Off→显式注入 `enable_thinking=false`**（Qwen3.8-27B 混合思考模型默认输出 reasoning_content，不显式关闭则仍在思考）；Low/Medium/XHigh→注入对应 reasoning_effort + enable_thinking=true）；
- `_thinkingGate` 锁保护状态迁移，`ThinkingModeChanged` 事件驱动 UI 底部面板显示。

**崩溃恢复管道**（详见 §4.6）：

- `TryCrashRecoverAsync`：CrashRecovery 双源检测（进程退出码 + 日志 bad_alloc 关键字）；
- `RecoverAliveAsync`：SSE keep-alive（`: keepalive\n` 每 5s）+ writeGate 写门控 + ProbeClientConnectedAsync + save n_saved>0 + freeGb<4 → budget*0.75 + 快照接续或全量重放；
- `RestartAndReplayAsync`：≤MaxAutoRestarts 次 EnsureRunningAsync + URI 重建 + 严格预算；
- 熔断器：10min ≥3 次 → IsTripped（UI 红色告警）。

**RestoreStats 命中率判定**（3.1，调度器侧轻量 mini 状态机，不搬 parser——parser 归属 MainForm）：

- **真值源**：print_timing 的 `prompt eval tokens`（唯一不受 wrapper 缓存干扰的 KV 复用证据）；
- **FIFO 归属**：`PrepareGatewayAsync` 对有快照的 key 入队 `(key, slot, wrapperHit, savedN)`，`OnServerOutput` 收到 prompt eval 行时弹最旧条目判定（TTL 60s 防错位）；
- **四象限判定**：eval ≤4096 → HitByDelta（增量命中）；eval×2 ≥ max(savedN, eval) → FullPrefill（restore 未生效）；中间态 MidRange 保守判 miss；对比 wrapperHit 计 false_miss / false_hit 误报率；
- **告警**：总命中率 <80% 黄警 / <50% 红警，状态迁移才触发（不重复），≥5 样本才评估；日志带「警告：/错误：」前缀 → LogFile.Classify 自动入 warn_error.log；
- **持久化**：config/restore_stats.json 原子写（tmp+rename，≥10s 且 dirty 才落盘）；UI 底部「Restore 命中率」卡片随每轮 print_timing 刷新。

### 3.9 LogFile + LogPipeline —— 统一异步日志管道（v2.11）

**架构**（方案 A）：四流共享全局单有界队列 + 单后台写线程批量消费。

```text
生产侧（任意线程）                    写线程（LogPipeline-Writer daemon）
LogFile.Append(line)                ──▶ Enqueue(Main, utc, line)
LogFile.SlotAppend(line)            ──▶ Enqueue(Slot, utc, line)
LogFile.DumpAppend(block)           ──▶ Enqueue(Dump, utc, block)
     │ lock(_gateForEnqueue)              │ Drain(512) → ProcessBatch
     │ 仅入队，零编码/分类/磁盘            │   ├─ Main: Classify → harness.log + warn_error.log（派生）
     ▼                                    │   ├─ Slot: slot.log
BoundedLineQueue (50k)                  │   └─ Dump: request_dump.log
     │ 满时按 QueueFullPolicy 丢弃        │ Flush 判定（≥150ms 或 ≥64KB）
     └──────────────────────────────────▶ │ 轮切（close→rename→reopen，写线程内）
```

- **生产侧**：`Enqueue` 一次 lock 仅入队（零编码/分类/磁盘），时间戳 `DateTime.UtcNow` 在 Enqueue 捕获（消除写线程时序漂移）；
- **队列**：全局单有界队列 50k 行（四流共享，≈10MB 上限）。满时按 `QueueFullPolicy` 丢弃——DropNewest（默认，保留历史）/ DropOldest，可配置运行时切换（UI ComboBox + `LogFile.Configure`）；
- **写线程**：`_wake.Wait(150ms)` tick → `Drain(512)` 批量出队 → `ProcessBatch` 逐条处理 → Flush 双阈值判定（≥150ms 或 ≥64KB）→ 轮切（close→rename→reopen，全在写线程内，无锁竞争）；
- **四流独立轮切**：harness.log（2MB）/ warn_error.log（5MB，派生自 main Classify）/ slot.log（2MB）/ request_dump.log（2MB），各自独立互不干扰；
- **IO 退避**：连续失败每条间隔 200ms Sleep + io_fail 累计计数（防磁盘满死循环打满 CPU）；
- **Shutdown drain**：停止接收 → drain 全部队列 → 最终 Flush；Join 3s 超时区分 drained/timeout（remain N lines lost）；
- **[LOG-PIPE] 埋点**（约束 C-4）：启动（4 流/队列/policy）/ dropped=N / io_fail=N / shutdown drained|timeout；
- **_recent 环形缓冲**（生产侧更新，仅 main 流）：`Append` 时同步更新 `_recent`（10 条），`SnapshotRecent()` 为 /__status__ 端点 recent_logs 数据源——UI 行为零变更；
- **Classify 四级分类**保留原位：**已知良性噪声前置过滤**（llama.cpp「model has unused tensor blk.*」→ Info）→ 中文关键字 → IWE 严重度正则 → 英文关键字；
- **LogFile 薄门面**：`Append`/`SlotAppend`/`DumpAppend` 委托 `LogPipeline.Enqueue`；静态类，尽力而为（写失败不抛异常）。

### 3.10 SystemMetrics —— 资源采样

- **手动触发**（v2.5）：去掉 2s 定时器轮询，改由系统资源页「手动刷新」按钮驱动；采样在 `Task.Run` 中执行（防重入），CPU 利用率、内存占用、GPU 显存（nvidia-smi）；
- `nvidia-smi` 调用带 WaitForExit 超时（C-009：防进程挂起阻塞采样线程）；
- `GetVramUsedMbAsync()`（static）供休眠后显存回落校验（C-006）；
- 崩溃恢复分支 A 的内存余量决策（freeGb<4 → 预算收紧）直接调用其采样方法。

### 3.11 LlamaCppMonitor —— llama.cpp 三接口监控（v2.5 新增）

**手动触发**采集服务，无后台轮询。点击「手动刷新」按钮时调用 `CaptureSnapshotAsync()`：

- **三接口并行请求**：`Task.WhenAll` 同时请求 `/slots`、`/props`、`/metrics`，各自独立容错——某接口失败时对应 Raw 为空、解析结果为空/默认值，不抛异常；
- **DTO**：
  - `LlamaSlotInfo`：id / id_task / state_name / n_ctx / tokens_cached / is_processing / speculative / pp_tps / tg_tps；
  - `LlamaGlobalProps`：约 30 个强类型字段 + `RawFields: Dictionary<string,string>`（递归展开原始 JSON 全部字段，含嵌套）；
  - `LlamaCppMonitorSnapshot`：CaptureAt + 三个 Raw 字段 + 解析结果；
- **FlattenJson**：递归展开 JSON 对象/数组为扁平 `key.path → value` 字典（嵌套用 `.` 连接，数组用 `[i]`），确保所有字段都展示；
- **HttpClient**：8s 超时，`Dispose()` 释放。

### 3.12 SlotAffinity —— 应用指纹 → 槽位绑定

- **应用指纹**（v2.16 规则配置化）：`GetAffinityKey` 由 static 硬编码 4 组 if 改为 `AffinityRuleMatcher` 规则引擎——规则表来自 config.json 的 `affinity_rules`（有序按 Priority 匹配：Header 取头值替换 KeyTemplate / HeaderValue 头值相等 → 固定 Key / UaAndHeaderPrefix UA 含子串且存在前缀头 → 固定 Key）；默认 4 条（dsh_rule_/webui_/trae_global/dsh_agent_global）与重构前逐字等价，新增业务 = 配置追加一条规则零代码改动；`AppNameOf` 亦由规则表派生显示名；**Step 4（UI 动态化）**：MainForm 自动强占/快照 8 个硬编码 CheckBox 改为由规则表动态生成（数量/显示名/前缀/tooltip 全配置化）；UiPrefixOf 推导写入 AutoPreemptiveApps/AutoSnapshotKeys 的前缀（Header→KeyTemplate 前段去分隔符、固定 Key→Key、显式 UiPrefix 优先）；新增业务配置加规则即自动出 UI checkbox 零代码；
- **GetSlot(headers, autoPreemptive)**：指纹查 slot_bindings.json 绑定表，未命中则分配空闲槽位并持久化；全槽强占满时排队等待（上限 30s）→ **E-5 两阶段**：锁内只做判定（TryAllocateLocked 原子分配），排队 Sleep 移到锁外，等待期间其他请求的 GetSlot/SetPreemptive/Snapshot 不再被阻塞（原 Sleep-in-lock 最长卡 30s）；
- **强占上限**（v2.7）：核心不变量 `强占数 ≤ slotCount - 1`（永远至少留 1 个槽给非强占新任务）。**cap 检查三路径**：① **启动时强制**——`EnforcePreemptiveCap()` 在构造后 / 唤醒后调用，从持久化恢复的绑定中裁剪超额强占到 cap（保留绑定，仅 Preemptive=false）；② **已有绑定刷新**——GetSlot 已有绑定路径中 autoPre 想设强占时检查 cap，已满则放弃（防"启动裁剪→下次请求又变回强占"死循环）；③ **新建绑定**——TryAllocateLocked 新建绑定时同样检查 cap，已满则放弃（防"驱逐了一个强占又建一个新的强占"导致 cap 失效）。全槽强占 + 新 key 也是强占 → 驱逐最早活跃的强占绑定（save KV），把槽让给当前请求。驱逐优先级：**Tool 链锁定 > 最早活跃的手动/自动强占**。保留策略为最早活跃（最久持有 = 最该让位），单槽下第一个主力 agent 稳定持有、不抖动；
- **LRU 驱逐**：槽位满时驱逐最久未使用的非强占绑定；
- **强占冻结**（Preemptive=true）：暂停 LRU 驱逐（§4.2 自动强占 + §4.5 Tool 链锁定共用此机制）；
- **自动强占**：AutoPreemptiveApps 前缀匹配 → 绑定强制 Preemptive=true；
- **Tool 链锁定**：messages 末条 role=tool → agent 工具循环进行中 → SetPreemptive(true) [KV-LOCK]；只解锁自己锁的键（_toolLockedKeys）[KV-UNLOCK]；`MarkToolLocked` / `UnmarkToolLocked` 同步标记到 SlotAffinity（强占上限驱逐优先级判定用）；
- 内部锁保护并发访问。

### 3.13 KvCacheManager —— KV 快照 save/restore

- **索引**：key→{slot, savedAt, nTokens, size} 内存索引 + kv_cache_index.json 持久化（独立于 slot_bindings.json）；
- **SaveAsync(key, slot)**：POST /slots/{id}?action=save → llama-server 落盘 .bin 到 KvCachePath；
- **RestoreAsync(key, slot)**：POST /slots/{id}?action=restore → 加载 .bin 恢复 KV；
- **DeleteCache(key)**：删除 .bin + 清索引（§6.3 续接成功后清理过期快照）；
- **四场景**：驱逐前 save / rebinding restore / 截断断点 save / 崩溃恢复 save+restore；
- 内部锁保护并发访问。

### 3.14 TokenGuard —— 上下文防护

- **真实分词计数**：调用后端 `/v1/tokenize` 端点对 messages 文本（role+content）计数（非字符估算、非整个 body——O-14 口径对齐，避免 model/temperature 等非上下文字段抬高计数）；
- **Prompt 头部开销预留**（v2.12）：`BuildMessagesText` 只统计消息数组（role+content），**不含** tools 工具 schema、system prompt、Jinja chat template 渲染的隐形 token。预算公式 `GetInputBudget()` = `CtxSize ÷ Parallel − ReservedOutputTokens − ReservedPromptOverhead`（默认 10240，UI 可配置），提前为隐形载荷预留坑位，防完整渲染后击穿窗口；
- **强制计量日志**（v2.12）：`MeasureAsync` 入口每次调用输出 `[TOKEN-GUARD] budget=..., msg_est=..., reserved_out=..., reserved_overhead=...`（消除"未裁剪无日志"排查盲区），供 Streamlit+DuckDB 统计 `prompt_overhead = real_full_prompt_token − msg_est_token`；
- **KV restore 重跑校验**（v2.12）：`ApplySlotAffinityAsync` 返回 `didRestore`，restore 后 saved_n 残留 + 新 prompt 叠加可能击穿窗口，强制重跑 TokenGuard 并输出日志；
- **400 自愈兜底**（v2.12）：`SendAndPipeAsync` 捕获 llama.cpp 400 "exceeds the available context size" → 激进裁剪（预算收紧 50%）→ 废弃 slot KV 缓存（强制全量 prefill）→ 重新提交请求；
- **轮次二分裁剪**（E-2）：超限时按轮预切分 + 二分求满足预算的最小删除轮数（≤log₂(轮数)+2 次 tokenize，替代旧实现「删一轮→全量重 tokenize」最坏 K+1 次），保留 system + 最后一轮，防 400；
- **内容兜底截断**（E-2）：单条消息超长时按保留比例减半迭代截断（≤5 轮收敛，替代固定 ratio 迭代 10 轮），头尾双保留并追加「已截断」标记；
- `GuardAsync(root, budget)` → DOM 版原地裁剪 `root["messages"]`（热路径复用同一棵树）；string 薄包装供崩溃恢复/续接等非热路径；tokenize 失败降级原样转发。最坏 tokenize 往返 10+ 次 → ≤6 次。

### 3.15 OutputContinuer —— SSE 管道与截断续接

- **HandleStreamAsync**：代理转发 + SSE 流式直通（按行缓冲逐段转发客户端）；
- **SSE 事件边界**：llama-server 原始 SSE 为 `data: {...}\n\n`（每事件后有空行），网关按行拆分转发时 `ForwardAsync` 补回 `\n\n` 结束符（held 行写出时同样补 `\n`），确保每个 SSE 事件以空行分隔——pi-ai 严格 JSON.parse 依赖此边界，缺失会导致 "Unexpected non-whitespace character after JSON"；
- **截断续接**：finish_reason=length → onTruncation 回调（save 断点快照）→ 自动续接（追加"继续"指令重放），客户端无感；
- **工具隔离**：续接请求检测到 tool_calls 即**不续接**、原样透传（防工具调用重复触发/损坏）；
- **写门控**：`writeGate`（SemaphoreSlim）保证 SSE 写入串行化（keep-alive 与数据帧不交错）；
- **MaxContinuations**：单请求最大续接次数（默认 10），超限停止并告警；续接全程受 ContinuationTimeoutSeconds（默认 300s）约束。

### 3.16 CrashRecovery —— bad_alloc 检测与熔断

- **崩溃判定（跨类协作）**：CrashRecovery 类内提供日志关键字源——`OnBackendLine` 捕获进程输出中的 bad_alloc 关键字并记录时间戳，`WasBadAlloc(60s)` 提供佐证窗口；进程死活判据（`_server.IsRunning`）与 5xx 响应体 "bad allocation" 关键字判定位于 SmartScheduler，二者汇合后形成实际双源；
- **RecordCrash()**：记录崩溃时间戳（无参，内部取当前时间）；
- **熔断器**：10min 窗口内 ≥3 次 → IsTripped=true（UI 红色告警 + 停止自动恢复）；
- **IsTripped**：只读属性，UI 每 2s 轮询；
- 静态类，内部锁保护时间戳队列。

## 4. 关键流程

### 4.1 启动流程

```text
Program.Main
  ├─ SetHighDpiMode(PerMonitorV2)
  ├─ 单实例 Mutex "Local\LlamaHarness"（已存在 → 弹框退出）
  ├─ EnableVisualStyles + UnhandledException 处理器

       ├─ Load AppConfig（config.json，数值兜底）

       ├─ AcceptLoopAsync 启动（异常重试 3 次）
       └─ 阶段 = Standby（待机稳态，常驻监听，无 llama-server 进程）
```

### 4.2 稳态循环（Standby ↔ Running）

```text
Standby ──推理请求──▶ WakeUpAsync ──WaitReady ok──▶ Warming ──预热完成──▶ Running
   ▲                                                            │            │
   │            闲置 IdleMinutes（默认 15min）+ 10s 观察期       │            │
   └──────── SleepNow（KV 快照 save → Kill 进程树） ◀────────────┘◀──────────┘
```

- 唤醒：StatsReset → BuildArgs → Start → WaitReady（探测 + body 校验）→ CpuAffinity.Apply；
- **Warming**：WaitReady 成功后、Running 前——eager restore（autoPre key 有快照者）+ dummy 预热（max_tokens=1，只碰无快照槽位）；≤60s，失败不阻塞转 Running；期间请求排队等待（_wakeTask 未完成）；
- 休眠：闲置定时器触发（inflight==0）→ 10 秒静默观察期（有新活动即取消）→ 逐槽 KV 快照 save → Kill → 3s 后查显存确认回落（C-006）→ Exited 回调回 Standby。

### 4.3 单请求全管道（ForwardAsync）

见 §3.3 ForwardAsync 全管道图（8 步顺序执行）。关键约束：

- **思考模式拦截**优先于一切（指令识别在网关侧，确认回复由后端模型生成）；
- **槽位亲和**在转发前确定（决定 --slots 路由 + KV 快照归属）；
- **TokenGuard** 在转发前裁剪（防 400）；
- **崩溃恢复**在 SSE 管道内检测（流中断时介入）；
- **§6.3 清理**最后执行（续接成功后删过期快照）。

### 4.4 KV 复用九场景

| # | 场景 | 触发条件 | 动作 | 标记 |
| - | ---- | -------- | ---- | ---- |
| §4.1 | 截断断点驻留 | finish_reason=length | onTrunc → save 快照 → 标记「截断待续接」→ 续接成功清理 / 失败保留 | [KV-SAVE] [KV-CLEANUP] |
| §4.2 | 空闲冻结防驱逐 | AutoPreemptiveApps 前缀匹配 | 绑定强制 Preemptive=true（暂停 LRU） | — |

| §4.4 | TokenGuard 裁剪前缀增量 | 裁剪后 messages 变化 | 前缀哈希重置基线（防误报 MISS） | [KV-HIT]/[KV-MISS] |
| §4.5 | Tool 链锁定 | 末条消息 role=tool | SetPreemptive(true)；只解锁自己锁的键 | [KV-LOCK] [KV-UNLOCK] |

| §4.9 | Warming eager restore（3.2） | 唤醒就绪后，**AutoSnapshotKeys** key 有磁盘快照（IsAutoSnapshotKey） | RunWarmingAsync 立即 restore + dummy 预热（成功记 _servedKeysThisRun 防重复） | [KV-RESTORE] |

### 4.6 崩溃恢复三分支

```text
  └─ 分支 C：客户端断开
```

## 5. 线程并发模型

| 线程/上下文        | 职责                                   | 同步机制                          |
| ------------------ | -------------------------------------- | --------------------------------- |
| UI 主线程（STA）   | MainForm 全部控件操作                  | BeginInvoke 编组后台事件          |
| Accept loop 线程   | HttpListener.AcceptAsync + 请求分发    | 异常重试 3 次（C-008）            |
| 请求处理线程       | HandleRequestAsync / ForwardAsync      | inflight++/-- (try/finally, C-002) |
| 进程 IO 线程       | llama-server stdout 逐行回调           | LlamaStatsParser 内部锁           |
| 手动刷新线程      | MonitorPanelView.Refresh（按钮触发，Interlocked 防重入）+ LlamaCppMonitor 三接口并行采集 | HttpClient 8s 超时 + Task.WhenAll |
| 定时器线程         | 闲置休眠 / P 核自愈 / UI metrics tick  | 阶段状态机原子迁移                |
| LogPipeline-Writer | 日志写线程（daemon）：Drain → ProcessBatch → Flush → 轮切 | _wake.Wait(150ms) tick + Shutdown Join(3s) |

**关键锁**：

| 锁                 | 保护对象                          | 所在模块          |
| ------------------ | --------------------------------- | ----------------- |
| `_kvStateGate`     | _truncPending / _toolLockedKeys / _prefixHashes / _servedKeysThisRun | SmartScheduler    |
| `writeGate`        | SSE 写入串行化（keep-alive 与数据帧不交错） | OutputContinuer   |
| `_thinkingGate`    | 思考模式状态机迁移                | SmartScheduler    |
| `_dumpLock`        | logs/request_dump.log 写入        | SmartScheduler    |
| `_gateForEnqueue`  | LogPipeline.Enqueue 入队（四流共享） | LogPipeline       |
| `lock(_gate)`      | BoundedLineQueue 内部队列 + LogFile._recent 环形缓冲 | LogPipeline / LogFile |
| 内部锁              | SlotAffinity / KvCacheManager / CrashRecovery 各自状态 | 各模块           |

**死锁规避原则**：跨模块调用不持锁（如 ForwardAsync 中 GetSlot → SaveAsync 顺序调用，不嵌套持锁）。

```json
      "trae_global":      { "slot": 1, "last_active": "2026-08-29T12:03:00.000+08:00" }
    }
  },
  "recent_logs": [ "12:03:01.123 [KV-HIT] ...", "... 共 10 条 ..." ]
}
```

> `recent_logs` 取 LogFile 环形缓冲（10 条，含 harness 侧全部日志）；单槽/多槽均返回 slots 信息（单槽时 count=1）。

### 6.2 后端端口（llama-server，动态）

- 实际端口 = 前端端口 +1 起探测（默认 8081）；
- OpenAI 兼容 API（/v1/chat/completions 等）；
- **--slots 端点**（KvCachePath 非空时启用，单槽/多槽均需）：
  - `POST /slots/{id}?action=save` → KV 快照落盘；
  - `POST /slots/{id}?action=restore` → KV 快照加载。

## 7. 设计决策

| #   | 决策                          | 理由 / 备选否决原因                                  |
| --- | ----------------------------- | ---------------------------------------------------- |
| D1  | 前端端口常驻 + 后端动态端口   | 客户端对接地址恒定；唤醒/休眠透明。备选：固定后端端口 → 端口冲突风险 |
| D2  | HttpListener 而非 ASP.NET Core | 零依赖、单进程、本机回环无需管理员权限               |
| D3  | SSE 直通 + 网关拦截           | 流式低延迟；网关只拦截必要字段（思考模式/TokenGuard）|
| D4  | P 核掩码硬编码默认值          | i5-13900F 固定硬件；配置可覆盖                       |
| D5  | print_timing 正则解析         | llama-server 无独立统计 API；日志是唯一数据源        |
| D6  | KV 复用（n_slots 路由，始终启用） | 多 agent 并发防跨槽漂移；单槽同样激活绑定+KV save/restore |
| D7  | KV 快照四场景（驱逐/重绑/截断/崩溃） | 全生命周期覆盖；.bin 落盘 RAMDisk 防重启丢失     |
| D8  | Tool 链末条判定               | 历史残留 tool 消息会永久误锁；末条 role=tool 才表示工具循环进行中 |
| D9  | 前缀指纹可观测（E-4）         | 轻量指纹（条数+role|content长度，零序列化零 SHA256）→ HIT/MISS 判定；restore 后重置基线防误报 |
| D10 | 思考模式状态机（全局跨请求）   | chat_template_kwargs 注入；_thinkingGate 锁保护迁移  |
| D11 | bad_alloc 三分支恢复          | 存活→快照接续 / 进程死→重启重放 / 客户端断→不重放    |
| D12 | SSE keep-alive + writeGate    | 崩溃恢复期间保活客户端无感；写门控防帧交错           |
| D13 | 熔断器（10min ≥3 次）         | 防无限重启循环；IsTripped 需人工介入                 |
| D14 | 零第三方 NuGet 包             | BCL 内置 HttpListener/HttpClient/System.Text.Json 够用 |
| D15 | WinForms 而非 WPF/AvalonUI    | 功能边界小，避免过度设计                             |
| D16 | 快照持久化 ≠ 槽位强占（v2.10） | `AutoSnapshotKeys` 只管首请求存档 + Warming eager restore；`AutoPreemptiveApps` 只管槽位冻结。单槽下 trae 享受崩溃恢复快照且 WebUI 可正常驱逐；多槽生产仍可用强占做常驻 Agent。备选否决：复用 AutoPreemptiveApps → 单槽下 trae 冻结槽位，WebUI 无法进入 |

### 7.1 后续开发约束原则（v2.10 写入）

以下四条为项目级硬约束，后续所有功能开发必须遵守：

| # | 约束 | 说明 |
| - | ---- | ---- |
| C-1 | **配置开关职责单一** | 禁止把多个独立完整能力耦合到同一个配置开关。一个配置项只控制一类职责（反例：AutoPreemptiveApps 曾同时承担"快照持久化 + 槽位强占"两职责，导致单槽场景无法只取其一 → v2.10 拆出 AutoSnapshotKeys） |
| C-2 | **复合行为拆组件** | 不在调度器内部写大量内嵌逻辑；拆分为接口组件，SmartScheduler 只做事件分发与编排（参照既有 CrashRecovery / TokenGuard / OutputContinuer / RestoreStats 组件化模式） |
| C-3 | **场景差异走组件组合** | 业务场景差异优先用「组件开关组合」解决，而不是新增大量分支 if-else（如：快照 + 强占 = 两个独立开关的组合，而非一个三态枚举） |
| C-4 | **组件独立日志埋点** | 每个组件必须有独立日志埋点，明确输出：组件是否启用、触发、执行结果（统一标记前缀如 [KV-SAVE] / [KV-RESTORE-JUDGE]，可 grep 可观测） |

## 8. 错误自愈矩阵

| 故障场景                | 检测方式                          | 自愈动作                              | 人工介入条件          |
| ----------------------- | --------------------------------- | ------------------------------------- | --------------------- |
| llama-server 启动失败    | WaitReadyAsync 超时               | 重试（≤3 次）→ 阶段回 Sleeping        | 连续失败              |
| 后端端口被占用           | 探测失败                          | 自动 +1 换端口                        | 端口耗尽              |
| P 核漂移                 | CpuAffinity.Heal 读回比对         | 重绑 P 核掩码                         | —                     |
| 显存未回落（休眠后）     | VerifyVramReleasedAsync（C-006）  | 告警日志                              | 反复出现              |
| 上下文超长 400           | TokenGuard 真实分词计数           | 轮次制裁剪 + 内容兜底截断             | —                     |
| 输出截断（finish_reason=length） | SSE 流检测                  | 自动续接（≤MaxContinuations）+ 断点快照 | 续接超限              |
| bad_alloc（进程存活）    | 5xx 响应体 + WasBadAlloc 日志佐证 | RecoverAliveAsync（keep-alive + 快照接续/重放） | 熔断触发          |
| bad_alloc（进程死亡）    | IsRunning=false（Exited 事件）    | RestartAndReplayAsync（≤MaxAutoRestarts） | 重启超限 / 熔断     |
| 客户端断开               | ProbeClientConnectedAsync         | 不重放，清理资源                      | —                     |
| KV restore 失败          | RestoreAsync 异常                 | 降级为全量重放                        | —                     |
| HttpListener accept 异常 | AcceptLoop 捕获                 | 重试 3 次 → RaiseStatus "监听失败"    | 连续失败              |
| nvidia-smi 挂起          | WaitForExit 超时（C-009）         | 跳过本轮采样                          | —                     |
| config/config.json 损坏  | Load() 反序列化异常               | 数值兜底 + 回退默认                   | —                     |
| UI 线程异常              | SetUnhandledExceptionMode         | 弹框提示 + logs/unhandled.log         | —                     |
| 后台线程异常             | AppDomain.UnhandledException      | logs/unhandled.log                    | —                     |

## 附录 A —— 黄金命令行

llama-server 实际启动命令（Parallel=2、KvCachePath=g:/temp 示例）：

```text
llama-server.exe -m "g:\models\Qwen3.8-27B-Ridge.gguf" --port 8081 -c 262144 -ngl 999 --parallel 2 --slots --slot-save-path "g:/temp" --no-kv-unified -t 8
```

- `--slots --slot-save-path`：KV 快照端点前提（KvCachePath 非空即拼接，单槽/多槽均需）；save-path 始终以引号包裹（防路径含空格断裂）；
- `--port`：后端端口（前端 +1 探测结果），非固定 8080；
- `-t 8`：P 核线程数（CpuAffinity 绑定后）。

## 附录 B —— 术语表

| 术语 | 含义 |
| ---- | ---- |
| 槽位亲和（Slot Affinity） | 应用指纹 → 固定槽位绑定，防多 agent 并发跨槽漂移 |
| 强占（Preemptive） | 暂停 LRU 驱逐的绑定标记（自动强占 / Tool 链锁定共用） |
| 断点快照 | finish_reason=length 时 save 的 KV .bin，续接失败保留供 rebinding/崩溃恢复 restore |
| keep-alive | SSE 保活帧（`: keepalive\n`），崩溃恢复期间维持客户端连接 |
| 熔断器（Circuit Breaker） | 10min ≥3 次崩溃 → IsTripped，停止自动恢复需人工介入 |
| 前缀指纹（E-4） | 轻量指纹（消息条数+各条 role|content长度，零序列化零 SHA256），KV HIT/MISS 可观测判定 |
| writeGate | SemaphoreSlim 写门控，SSE 写入串行化（keep-alive 与数据帧不交错） |
| n_slots 路由 | llama-server 槽位路由机制（单槽/多槽均启用），KV 快照按槽隔离 |
| print_timing | llama-server 日志中的推理统计块（task ID / 速度 / 投机命中率等） |
| P 核亲和 | Intel 混合架构 CPU 上把 llama-server 绑定纯 P 核（防 E 核漂移） |
| 轮次二分裁剪（E-2） | TokenGuard 超限时按轮预切分 + 二分求最小删除轮数（≤log₂(轮数)+2 次 tokenize），保留 system + 最后一轮 |
| rebinding restore | 槽位变更后从旧槽快照加载 KV 到新槽（重启自愈场景） |
