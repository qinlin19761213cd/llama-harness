## 五、关键修复详解

### 5.1 H1 — MetricKeys × ValueOf 键覆盖错位（最高影响）

**问题**: 审计扫描发现 `MetricsPerf.cs` 定义了 27 个 `MetricKeys` 枚举值，但 `PerfAnalyzer.ValueOf` 只覆盖 11 个 case。配置文件里引用的新键名（如 `prefill_kv_total_ms`、`backend_queue_depth`）全部返回 `null`，导致告警规则静默失效。

**修复**:
```csharp
// 修复前：11 个 case
// 修复后：28 个 case（含 IsThroughputMetric 扩展）
public static PerfPoint? ValueOf(this MetricKeys key, IEnumerable<PerfPoint> pts)
{
    PerfPoint? Find(Func<PerfPoint, bool> pred) => pts.FirstOrDefault(pred);
    return key switch
    {
        MetricKeys.BackendLatencyMs      => Find(p => p.BackendLatency.HasValue),
        // ... 原有 10 个 ...
        MetricKeys.PrefillKvTotalMs      => Find(p => p.PrefillKvTotal.HasValue),      // 新增
        MetricKeys.BackendQueueDepth     => Find(p => p.QueueDepth.HasValue),            // 新增
        MetricKeys.SlotAffinityHitRate   => Find(p => p.SlotAffinityHitRate.HasValue),  // 新增
        MetricKeys.TotalTokensPerSec     => Find(p => p.TokensPerSec.HasValue),          // IsThroughputMetric 标记
        // ... 共 28 case ...
        _ => null,
    };
}
```

**影响面**: 所有基于 `MetricKeys` 配置的阈值告警规则恢复生效。

---

### 5.2 H2 — SystemMetrics CPU 采样四字段无锁

**问题**: `GetCpuPercent` 在采样瞬间读写 `_prevTotalProcessorTime`、`_prevIdleTime`、`_currentTotalProcessorTime`、`_currentIdleTime` 四个字段。多线程同时调用时可能读到半更新状态，导致 CPU 百分比失真（出现负数或 >100%）。

**修复**:
```csharp
private readonly object _cpuGate = new();
public double GetCpuPercent()
{
    lock (_cpuGate)  // 新增
    {
        // ... 原有的采样 + 计算逻辑不变 ...
    }
}
```

**影响面**: 系统资源页 CPU 百分比显示稳定，不再出现异常波动。

### 5.3 M1 + M7 + M8 — SmartScheduler.Http 响应关闭 + 异步安全

这是 P1 中最有价值的组修复——覆盖 HttpListenerResponse 资源泄漏 + 同步阻塞 + 超时失效三个问题。

| 问题 | 修复 |
|------|------|
| M1: TryRecover 失败路径未 Close ctx.Response | 在 PumpResponseAsync 的 finally 段统一 Close；即使 TryRecover return true 跳过泵流，Response 也不会泄漏 |
| M7: HandleHealth `.GetAwaiter().GetResult()` | 改 `async Task<bool>`，用 `await WriteJsonAsync` 替代同步阻塞。当前线程池安全，但 UI 线程调用会死锁 |
| M8: handlerTask 超时后继续跑 | `Task.Run` 传 `handlerCts.Token`；handlerTask 内部两处加 `ThrowIfCancellationRequested`；超时后闭包能被底层取消，不会写已 Close 的 Response |

**影响面**: HttpListener 连接泄漏归零；健康检查不再阻塞线程池线程；300s 看门狗超时真正生效。

---

### 5.4 M14 — PruneStaleBindings 从"启动跑一次"到"每次 GetSlot 顺带跑"

**问题**: `SlotAffinity.PruneStaleBindings` 只在启动时调用一次。长时间运行后 stale 绑定（槽位已消失但 affinity 表还在）持续累积，导致 GetSlot 遍历成本线性增长。

**修复**:
```csharp
// GetSlot 方法锁内
lock (_gate)
{
    PruneStaleBindings();  // [P1-M14] 每次 GetSlot 顺带清理
    // ... 原有匹配逻辑 ...
}
```

**影响面**: 运行时 stale 绑定保持低水位，GetSlot O(n) 遍历不会随时间退化。

---

### 5.5 M13 + M15 — RestoreStats 队列 + KvCacheManager 超时

| 模块 | 问题 | 修复 |
|------|------|------|
| RestoreStats._pending | 无容量上限，后端长时间静默时队列持续入队 → 内存缓慢累积 | `MaxPendingQueueCapacity=256`，超限时 Dequeue 最旧条目 |
| KvCacheManager.ClearAllAsync | `Task.WhenAll(tasks)` 不接受 CancellationToken → 超时保护形同虚设 | `WhenAny(Task.WhenAll(tasks), Task.Delay(timeout, ct))` 真正超时 |

## 六、降级项核心论点

审计发现的 19 条中，有 4 条需要特别说明：

| 编号 | 审计描述 | 实际情况 |
|------|---------|---------|
| SetPhase TOCTOU | "需 Interlocked.CompareExchange" | **误判**。已用 `Volatile.Read(ref _phase)` + `Volatile.Write(ref _phase, ...)`，C# Volatile 语义提供 acquire/release 内存屏障，多线程安全 |
| M3 OutputContinuer 无取消 | "整条管道无 CancellationToken 贯穿" | **误判**。HandleStreamAsync 内部有 `CancellationTokenSource(ContinuationTimeoutSeconds)`；客户端断开触发 IOException 被 catch；取消通路完整 |
| M9 LogPipeline.Shutdown 竞态 | "并发 Enqueue 窗口竞态" | **接受**。关闭阶段丢最后几条日志是可接受的尽力而为语义；修复需 >100 行 drain 队列 + CTS |
| M18 TokenGuard surrogate pair | "Substring 切断 Unicode 代理对" | **定位偏差**。审计指向的 L170-L174 是判定逻辑，不是截断逻辑；实际截断逻辑未用 Substring |
