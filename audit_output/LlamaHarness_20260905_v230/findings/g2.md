## KvCacheManager.cs

### [中] DoSaveAsync 文件名不含 slot 编号，依赖上层不变量

**文件行号**: KvCacheManager.cs L155-158  
**类型**: 数据正确性 / 并发安全  
**触发**: 上层 Pipeline 打破"每 key 固定 slot"约定时，同一 key 被并发 save 到不同 slot  
**后果**: 后写入的 .bin 文件覆盖先写入的，导致一个 slot 的 KV 快照丢失；或者 restore 到错误的 slot。文件只按 key 命名（`Sanitize(key).bin`），不区分 slot。  
**代码片段**:
```csharp
// P2-6：文件名不含 slot 编号——依赖"每 key 由亲和路由绑定固定 slot"的上层不变量
var resp = await _backend.SlotSaveAsync(slot, $"{Sanitize(key)}.bin", effCt);
```

**证据链三要素**:
- **前提**: 文件名 `{Sanitize(key)}.bin` 不包含 slot 编号
- **触发条件**: 两个不同 slot 对同一个 key 并发调用 `DoSaveAsync`
- **后果**: 文件系统层面先保存后覆写，只有最后一次保存生效；`_inflightSaves` 的去重键是 `slot#key` 正确区分，但文件 IO 层面无隔离

### [中] ClearAllAsync 超时保护失效 —— WhenAll 不响应 CancellationToken

**文件行号**: KvCacheManager.cs L353-364  
**类型**: 性能 / 资源管理  
**触发**: DoSaveAsync 被传入的 CancellationToken 不自动取消时（异常路径/后端挂起）  
**后果**: ClearAllAsync 理论上循环 50 × 1s = 50s，但 CTS 只在 WhenAll **完成后**才检查，WhenAll 本身不接受 CancellationToken。单个 save 默认 30s 上限，5s CTS 形同虚设。  
**代码片段**:
```csharp
var cts = new CancellationTokenSource(TimeSpan.FromSeconds(5));
for (int i = 0; i < 50; i++)
{
    Task[] inflight;
    lock (_gate) { if (_inflightSaves.Count == 0) break; inflight = _inflightSaves.Values.ToArray(); }
    try { await Task.WhenAll(inflight); } catch { }
    if (cts.Token.IsCancellationRequested) break; // 只在 WhenAll 之后检查
}
```

**建议**: 用 `Task.WhenAny` + `Task.Delay(1s)` 替代，使 CTS 真正起作用。

### [观察] TrimToQuota 每次 save 结束都触发

**文件行号**: KvCacheManager.cs L198  
**类型**: 性能  
**触发**: 高频 save 场景（会话切换频繁）  
**后果**: 每次 DoSaveAsync finally 都 fire-and-forget 调 TrimToQuota。TrimToQuota 内有 `Directory.GetFiles(_cachePath, "*.bin")` 和每个文件的 FileInfo 读取。虽然早期 return 保护了磁盘配额以下的情况，但仍然有不必要的文件枚举开销。  
**代码片段**:
```csharp
// P2-5：save 结束后异步触发磁盘配额 LRU 清理（fire-and-forget）
_ = Task.Run(() => TrimToQuota());
```

**建议**: 增加节流（如 60s 内最多跑一次）或计数器（累积 10 次 save 跑一次）。

## SlotAffinity.cs

### [中] SlotAffinity.Save() 在锁内执行完整文件 IO 链 —— 热路径阻塞

**文件行号**: SlotAffinity.cs L290 (TryAllocateLocked) + L449-479 (Save)  
**类型**: 性能 / 并发吞吐量  
**触发**: GetSlot 热路径（新 key 绑定 / LRU 驱逐时）  
**后果**: Save() 内部依次执行 EnsureConfigDir → Json 序列化 → File.WriteAllText → File.Move，全部在 `lock(_gate)` 内。磁盘 IO 抖动会阻塞所有其他 GetSlot/MarkToolLocked/SetPreemptive 调用。  
**代码片段**:
```csharp
// TryAllocateLocked 锁内：
_bindings[key] = new Binding { ... };
Save(); // ← 完整文件 IO 链在锁内
```

**对比**: KvCacheManager.RecordSave 已做到"锁内只更新内存 + 构建 JSON，锁外写 File.WriteAllText"。SlotAffinity 应同步改造。

### [中] 绑定表 PruneStaleBindings 只在启动时运行一次 —— 运行时 stale 累积

**文件行号**: SlotAffinity.cs L68 + L484-497  
**类型**: 资源泄漏  
**触发**: 长期运行 + 大量动态 key（如 Header 规则 `dsh_rule_{value}` 的 value 不断变化）  
**后果**: PruneStaleBindings 仅在构造函数调用一次。运行期间 key 的 LastActive 不再刷新（LRU 刷新时只更新内存不做定期淘汰），过期绑定只能等被 LRU 驱逐。如果 key 数量 > slotCount，老 stale 绑定可能永远留在字典里，`_bindings` 持续增长。  
**代码片段**:
```csharp
// 构造函数内：
Load();
PruneStaleBindings(); // ← 只跑一次
EnforcePreemptiveCap();
```

**建议**: 在 GetSlotCore 每次刷新绑定 LastActive 时顺便检查该绑定是否已超过 StaleBindingDays，或者后台定时器每小时跑一次 Prune。

### [低] 构造函数内 EnforcePreemptiveCap 依赖 Load 顺序 —— 耦合脆弱

**文件行号**: SlotAffinity.cs L67-69  
**类型**: 代码可维护性  
**触发**: 未来有人调整构造函数内调用顺序  
**后果**: Load() 必须在 EnforcePreemptiveCap() 之前，否则裁剪的是空绑定表。隐式顺序依赖，如果有人把 EnforcePreemptiveCap 提到 Load 之前，不会报错但功能静默失效。  
**代码片段**:
```csharp
Load();                    // 先加载持久化绑定
PruneStaleBindings();      // 再清理过期
EnforcePreemptiveCap();    // 最后裁剪超额强占
```

## AffinityRuleMatcher.cs

### [高] Array.Sort 原地排序可能修改调用方数组

**文件行号**: AffinityRuleMatcher.cs L20-21  
**类型**: 数据正确性 / 隐藏副作用  
**触发**: 调用方传入的 `rules` 本身就是 `AffinityRule[]` 数组  
**后果**: `rules as AffinityRule[]` 返回原始引用，`Array.Sort` 原地重排。调用方的 `_rules`（如果是 backing array）顺序被永久打乱。后续 Match 调用虽然按 Priority 正确，但如果调用方有其他依赖原始数组顺序的代码，会静默出错。  
**代码片段**:
```csharp
var arr = rules as AffinityRule[] ?? rules.ToArray();
Array.Sort(arr, (a, b) => a.Priority.CompareTo(b.Priority));
```

**修复**: 改为始终 `rules.ToArray()` 不做 as-cast，或 `Array.Sort(arr, ...)` 前 arr 是 `ToArray()` 的结果即可。

### [低] Header 匹配模式未校验 KeyTemplate 包含 {value} 占位符

**文件行号**: AffinityRuleMatcher.cs L35-41  
**类型**: 健壮性 / 配置校验  
**触发**: AffinityRule 配置的 Match=Header 但 KeyTemplate 忘写 {value}  
**后果**: `r.KeyTemplate.Replace("{value}", hv)` 返回原 KeyTemplate，所有不同头值的请求得到相同亲和 key，导致不同业务被路由到同一槽位。不会崩溃，但静默降低隔离性。  
**代码片段**:
```csharp
case AffinityMatchType.Header:
{
    var hv = headers[r.Header];
    if (string.IsNullOrEmpty(hv)) return null;
    if (hv.Length > MaxHeaderValueLength) return null;
    return r.KeyTemplate.Replace("{value}", hv); // ← KeyTemplate 可能不含占位符
}
```

**建议**: 在构造函数或首次 Match 时校验配置完整性，或 TryMatch 内检测 KeyTemplate 不含 `{value}` 时记录警告。

## RestoreStats.cs

### [中] _byKey + _refPrefillTpsBy 字典无界增长 —— 长期运行内存泄漏

**文件行号**: RestoreStats.cs L28 + L34  
**类型**: 资源泄漏 / 数据完整性  
**触发**: key 持续增加（如动态业务 key 或 unknown 不断变化）  
**后果**: `_byKey` 在 OnPromptEval 每次遇到新 key 都 Add，无删除逻辑；`_refPrefillTpsBy` 同理。长期运行 + 大量 key → 内存持续增长无上限。即使 slot 绑定表淘汰了该 key，RestoreStats 仍保留其历史统计。  
**代码片段**:
```csharp
private readonly Dictionary<string, KeyStats> _byKey = new(StringComparer.OrdinalIgnoreCase);
private readonly Dictionary<string, double> _refPrefillTpsBy = new(StringComparer.OrdinalIgnoreCase);

// OnPromptEval 内（L180-181）：
if (!_byKey.TryGetValue(p.Key, out var ks))
    _byKey[p.Key] = ks = new KeyStats();
```

**建议**: 增加 LRU 上限（如 256 条），或在 SlotAffinity 驱逐绑定事件时同步删除对应 _byKey 条目。

### [中] _pending 队列无容量上限 —— RecordRequest 持续入队不阻塞

**文件行号**: RestoreStats.cs L27 + L132-138  
**类型**: 资源泄漏  
**触发**: 后端长时间不输出 prompt eval 行（llama-server 重启、卡死、或非推理请求）  
**后果**: RecordRequest 只入队，OnPromptEval 是唯一出队路径。TTL 清理在 OnPromptEval 内被动执行——如果 OnPromptEval 长时间不被调用，_pending 队列持续增长。PendingTtl=60s 只是在出队时才检查过期，过期条目不会主动被清理。  
**代码片段**:
```csharp
private readonly Queue<Pending> _pending = new();

public void RecordRequest(string key, int slot, bool wrapperHit, int savedN)
{
    lock (_gate)
    {
        if (savedN > _maxSavedN) _maxSavedN = savedN;
        _pending.Enqueue(new Pending { ... }); // ← 只入队，无上限
    }
}
```

**建议**: 增加队列容量上限（如 1024），超限时 Dequeue 最旧条目丢弃。

### [观察] OnPromptEval 两阶段锁存在理论 TOCTOU 窗口

**文件行号**: RestoreStats.cs L146-228  
**类型**: 观察  
**触发**: RecordRequest 和 OnPromptEval 高并发交叉调用  
**后果**: 阶段 1（L146-152）在锁内 Dequeue Pending，释放锁后调用 Judge()，然后阶段 2（L162）又拿锁更新统计。窗口内 RecordRequest 可能入队新条目——不影响正确性（Judge 是纯计算），但 OnPromptEval 是两次锁操作，增加了锁竞争次数。属于设计取舍而非 bug。
