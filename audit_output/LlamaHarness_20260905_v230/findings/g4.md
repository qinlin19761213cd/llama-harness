## 发现详情

### [中] MainForm._tooltip 未 Dispose（Component 资源泄漏）

- **文件行号**: `MainForm.Ui.cs:82`
- **类型**: 资源泄漏（Component 未 Dispose）
- **触发**: 进程关闭时 MainForm.Dispose 不会被 ToolTip 显式调用，依赖 GC 最终器回收
- **后果**: 违反 .NET IDisposable 规范；ToolTip 持有 Component 内部 GDI 资源和窗口句柄，在调试器中会看到 `System.Windows.Forms.Timer` 终结器日志；若未来 MainForm 支持多实例或快速重建，会积累 Component 对象
- **代码**:

```csharp
// MainForm.Ui.cs:82
private readonly ToolTip _tooltip = new();
// ... 40+ 处 _tooltip.SetToolTip(...) 调用 ...
// 但 OnFormClosing (MainForm.cs:169-199) 中无 _tooltip.Dispose()
// MainForm 也未重写 Dispose(bool)
```

- **建议**: 在 `OnFormClosing` 或重写 `Dispose(bool disposing)` 中加入 `_tooltip?.Dispose()`；推荐重写 Dispose 以便 Designer 自动生成的 `components` 容器也一并清理。

### [中] UiTheme.IconCache 无锁保护，LoadIcon 非线程安全

- **文件行号**: `UiTheme.cs:47,54,88`
- **类型**: 线程安全隐患（非线程安全的 Dictionary 并发读写）
- **触发**: 若未来有后台线程（如资源预加载）调用 `UiTheme.LoadIcon`，会与 UI 构建线程并发读写 IconCache
- **后果**: `Dictionary` 非线程安全，并发写入可能抛 `InvalidOperationException: Operations that change non-concurrent collections ...`，或导致键丢失 / 值错乱；当前版本 LoadIcon 仅在 UI 构建阶段（单线程）调用，暂无实际触发路径
- **代码**:

```csharp
// UiTheme.cs:47
private static readonly Dictionary<string, Image> IconCache = new(StringComparer.OrdinalIgnoreCase);

// UiTheme.cs:54-88 — 无 lock 保护
public static Image? LoadIcon(string fileName)
{
    if (IconCache.TryGetValue(fileName, out var cached)) return cached;  // 读
    // ...
    IconCache[fileName] = img;  // 写
    return img;
}
```

- **建议**: 对齐 FontCache 的做法，引入 `private static readonly object IconGate = new();` 并用 `lock (IconGate)` 包裹整个 LoadIcon 方法体；或改用 `ConcurrentDictionary<string, Image>`。

### [中] MarkdownRenderer.StripMdInline 每次调用新建 3 个 Regex（GC 压力）

- **文件行号**: `MarkdownRenderer.cs:126-128`
- **类型**: 性能隐患 + GC 压力
- **触发**: 渲染 Markdown 文档时，每个行内 Markdown 都会触发 StripMdInline；大文档（数百行）时 Regex 对象频繁创建/回收
- **后果**: Regex 编译开销 + 短命对象堆积到 Gen 0，可能引发频繁 GC；每次 ShowDocInPanel 都会触发完整渲染
- **代码**:

```csharp
// MarkdownRenderer.cs:126-128
public static string StripMdInline(string text)
{
    var s = System.Text.RegularExpressions.Regex.Replace(text, @"\*\*(.+?)\*\*", "$1");
    s = System.Text.RegularExpressions.Regex.Replace(s, @"`(.+?)`", "$1");
    s = System.Text.RegularExpressions.Regex.Replace(s, @"\[(.+?)\]\(.*?\)", "$1");
    return s;
}
```

- **建议**: 把 3 个 Regex 提升为 `static readonly` 字段并预编译：
  ```csharp
  private static readonly Regex _boldRe = new(@"\*\*(.+?)\*\*", RegexOptions.Compiled);
  private static readonly Regex _codeRe  = new(@"`(.+?)`", RegexOptions.Compiled);
  private static readonly Regex _linkRe  = new(@"\[(.+?)\]\(.*?\)", RegexOptions.Compiled);
  ```

### [低] MainFormPresenter.OnClearCacheClickedAsync 从 UI 线程调用 InvokeOnUiSync —— 隐式依赖 WinForms 同步执行语义

- **文件行号**: `MainFormPresenter.cs:132`
- **类型**: 代码可维护性隐患（隐式依赖特定运行时行为）
- **触发**: `async void OnClearCacheClicked` 从 UI 线程启动，第一个 `await`（行 142）之前全部代码在 UI 线程同步执行。行 132 的 `InvokeOnUiSync` 实际上是 UI 线程调用 `Invoke`
- **后果**: WinForms 中 UI 线程调用 `Invoke` 会同步执行委托（不走消息队列），当前正确。但若未来有人把这段 MessageBox 逻辑重构到后台线程调用，`InvokeOnUiSync` 会阻塞后台线程等待 UI 线程处理——此时若 UI 线程恰好也在等待后台线程（如 `await Task.Run` 的 continuation 需要 UI 线程），就会形成经典死锁
- **代码**:

```csharp
// MainFormPresenter.cs:132 —— 在 await Task.Run 之前（UI 线程）
var confirm = _view.InvokeOnUiSync(() => MessageBox.Show(_view,
    "确定清空所有 KV Cache 缓存？\n...",
    "确认", MessageBoxButtons.YesNo, MessageBoxIcon.Question));
```

- **建议**: 在 `InvokeOnUiSync` 方法上加注释说明"从 UI 线程调用会同步执行委托（非队列化）"；或直接在 Presenter 中调用 `MessageBox.Show`（行 132 当前就在 UI 线程，完全不需要 InvokeOnUiSync 包装）。

### [低] MainForm.Ui.cs 大量硬编码 Color.FromArgb 魔法值

- **文件行号**: `MainForm.Ui.cs:31,37-78,123,230-247,357-385,476-481` 等

### [观察] LogView 缺少 IDisposable 实现，依赖手动 StopAndFlush 调用

- **文件行号**: `LogView.cs:13,76-80`
- **类型**: 资源治理不完整
- **说明**: LogView 持有 `_logFlushTimer`（System.Windows.Forms.Timer）。当前依赖 MainForm.OnFormClosing 调用 `_logView.StopAndFlush()` 来停止定时器。如果窗体崩溃或异常退出（Application.Run 抛异常进入 catch），StopAndFlush 不会被调用，定时器会在 GC 回收 LogView 时由终结器停止——这个过程可能延迟数十秒，期间 Tick 事件仍会触发 Flush（但此时 RichTextBox 可能已不可用）。
- **建议**: 给 LogView 加 `public void Dispose()`（或重写 UserControl 的 Dispose），内部调用 StopAndFlush + 基类 Dispose；然后 MainForm.Dispose(bool) 中显式调用。

### [观察] Program.cs 单实例 Mutex 在 Application.Run 异常路径下的持有窗口

- **文件行号**: `Program.cs:13-37`
- **类型**: 观察（当前可接受）
- **说明**: `using var singleton = new Mutex(...)` 作用域覆盖整个 Main 方法。若 `Application.Run(new MainForm())` 抛异常进入 catch，Mutex 会在 MessageBox.Show 阻塞期间持续持有。单实例场景下这是合理的——异常退出时不应允许第二个实例启动。但 catch 块之后（MessageBox 关闭后）using 结束，Mutex 释放，异常退出的进程会干净退出。正确做法。
- **建议**: 可在 catch 块末尾显式 `singleton.Dispose()` 提前释放，但非必要。

### [观察] MainFormPresenter._schedSlotBindingChangedHandler / _schedSlotLogHandler 未经 InvokeOnUi 包装，但设计自洽

- **文件行号**: `MainFormPresenter.cs:62-63`
- **类型**: 观察（设计正确性）
- **说明**: Presenter 层直接调用 `_slot.RefreshBindings()` 和 `_slot.OnSlotLog(line)`，未包装 InvokeOnUi。但 SlotPanelView 内部通过构造函数注入的 `_invokeOnUi` 自行切回 UI 线程（见 `SlotPanelView.cs:80-84,92`）。这与 MainFormPresenter 中其他 handler 统一先 InvokeOnUi 再调用 View 的模式**不一致**——`_schedLogHandler`（行 44）直接调 LogView.Append（内部有 lock），`_schedSlotLogHandler`（行 63）直接调 SlotPanelView.OnSlotLog（内部有 InvokeOnUi）。
- **建议**: 统一约定：要么 Presenter 层统一 InvokeOnUi，要么 View 层各 handler 内部自行处理。建议后者更解耦（View 知道自己操作 UI，Presenter 不需要关心），但应在代码注释中明确这个设计约定。
