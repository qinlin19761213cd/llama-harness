### [High] MetricKeys "唯一权威注册表" 与 PerfAnalyzer.ValueOf 键覆盖严重错位，大量注册键在 EvaluatePoints 中不被识别

**文件**：MetricKeys.cs（全部注册常量）、PerfAnalyzer.cs 行 170–183（ValueOf 模式匹配）、PerfAnalyzer.cs 行 32–36（Defaults 中的键）
**类型**：契约破坏——"新增业务/改阈值 = 配置追加一条，零代码改动"的配置驱动前提失效
**触发**：用户在 config.json `perf_thresholds` 中使用 MetricKeys 注册表定义的键（如 `"gen_tps"` / `"prompt_eval_tps"` / `"vram"` / `"mem"`），或未来 v2.22+ 的阈值规则作者按 MetricKeys.All 列表追加。

**证据链**：

1. MetricKeys 注册表声明："任何新增/修改指标必须同时改本类与注册表"（行 4-5），暗示其键应在整个监控管道中通用。
2. PerfAnalyzer.ValueOf 是 EvaluatePoints 读取指标值的**唯一入口**（行 203 `var v = ValueOf(pt, rule.Metric);`）。
3. 下表列出 MetricKeys.**全部注册键** vs ValueOf 覆盖情况：

**ValueOf 仅覆盖 12 个键（其中 3 个是 MetricKeys 注册的），而 MetricKeys.All 列表有 27 个键**。近 90% 注册键在 EvaluatePoints 中使用时返回 null（行 204 `if (v == null) { runWarn = 0; runCrit = 0; continue; }`），规则被静默跳过，用户看不到任何告警。

**后果**：配置驱动阈值规则的核心契约被破坏。开发者按 MetricKeys 文档使用 `"gen_tps"` 而非 `"tg_tps"` 写规则，该规则在生产环境中**完全不生效**且无任何报错提示。PerfThresholdRule.Defaults 中仍使用旧键 `"tg_tps"`（正确匹配 ValueOf）形成了意外的"内部可用、注册表不可用"分裂状态。

**修复建议**：ValueOf 模式匹配中补齐 MetricKeys 注册的所有键名，与 ValueOf 已有键建立等价：

```csharp
// PerfAnalyzer.ValueOf 补齐 MetricKeys 注册表键：
public static double? ValueOf(PerfPoint p, string metric) => metric switch
{
    "cpu" or "cpu_percent" => p.CpuPercent,
    // MetricKeys.Vram = "vram"  + 旧键
    "vram" or "vram_mb" or "vram_used_mb" => p.VramUsedMb,
    // MetricKeys.VramTotal = "vram_total"  + 旧键
    "vram_total" or "vram_total_mb" => p.VramTotalMb,
    // MetricKeys.Mem = "mem"  + 旧键
    "mem" or "mem_gb" => p.MemUsedGb,
    "mem_total" or "mem_total_gb" => p.MemTotalGb,
    // MetricKeys.PromptEvalTps = "prompt_eval_tps" + 旧键
    "prompt_eval_tps" or "pp_tps" or "prompt_tokens_per_second" => p.PpTps,
    // MetricKeys.GenTps = "gen_tps" + 旧键
    "gen_tps" or "tg_tps" or "tokens_per_second" => p.TgTps,
    "tok" => p.TokensCached,
    "ctx" => p.CtxUsedPct,
    "slots" => p.SlotsProcessing,
    // MetricKeys.Inflight = "req_inflight" + 旧键
    "req_inflight" or "inflight" => p.Inflight,
    // MetricKeys 累积型指标补齐：
    "kv_hit_delta" => p.KvHitDelta,
    "kv_false_miss" => p.KvFalseMiss,
    "saved_n" => p.SavedN,
    "kv_full_prefill" => p.KvFullPrefill,
    "kv_reuse_tokens" => p.KvReuseTokens,
    "kv_reuse_saved_ms" => p.KvReuseSavedMs,
    "evict_count" => p.EvictCount,
    "preempt_trigger" => p.PreemptTrigger,
    "log_dropped_lines" => p.LogDroppedLines,
    "log_flush_cost_ms" => p.LogFlushCostMs,
    _ => null,
};
```

### [Medium] 吞吐类告警负载门控硬编码缺失 MetricKeys 新键名 `"gen_tps"` / `"prompt_eval_tps"`

**文件**：PerfAnalyzer.cs 行 202（IsIdlePoint 负载门控）
**类型**：字符串匹配硬编码 + 命名漂移
**触发**：阈值规则使用 MetricKeys.GenTps（"gen_tps"）或 MetricKeys.PromptEvalTps（"prompt_eval_tps"）时。

**代码片段**：

```csharp
// 行 202 —— 仅覆盖旧键名
if ((rule.Metric == "tg_tps" || rule.Metric == "pp_tps") && IsIdlePoint(pt)) continue;
```

**后果**：使用 MetricKeys 新键名的吞吐类阈值规则在系统空闲时不会跳过（不会 continue），会把 `tg_tps=0` 的空闲数据点也算入连续越限次数，导致每 5 分钟周期性误报吞吐骤降告警（如 tg_tps 持续 < 10 达到 MinDurationSeconds=30）。

**修复建议**：补齐新键名匹配，或引入 `IsThroughputMetric(metric)` 辅助方法集中判断：

```csharp
private static bool IsThroughputMetric(string m) =>
    m == "tg_tps" || m == "gen_tps" || m == "tokens_per_second" ||
    m == "pp_tps" || m == "prompt_eval_tps" || m == "prompt_tokens_per_second";

// 行 202:
if (IsThroughputMetric(rule.Metric) && IsIdlePoint(pt)) continue;
```

### [Medium] PerfAnalyzer 静态状态机字典 _curLevel 无容量上限，长期运行会持续增长（虽然 key 数量有限但无清理由）

**文件**：PerfAnalyzer.cs 行 108–109（_lastAlarmUtc / _curLevel）、行 146–149（ResetAlarmState）
**类型**：无界增长风险（低概率）
**触发**：用户在配置中动态增删 PerfThresholdRule（规则 Metric key 集合变化）→ _curLevel 中旧规则 key 永远不会被 Remove（仅在 OnRecover 中 Remove，但旧规则 key 永远不会触发 EvaluatePoints 的 else 分支）。

**实际**：当前是静态配置驱动，规则集在进程启动时固定，key 集合有限（≈ 27 个注册键）。但 PerfAnalyzer 注释"纯函数、无内部状态"（行 95）与事实矛盾——它维护了两个可变静态字典。如果未来有规则热更新，旧 key 会泄漏。

**修复建议**：在 ResetAlarmState 之外，EvaluatePoints 执行前先清理不在当前 rules 列表中的 Metric key：

```csharp
// 在 EvaluatePoints 开头：
lock (_alarmLock)
{
    var activeMetrics = new HashSet<string>(rules.Select(r => r.Metric));
    var stale = _curLevel.Keys.Where(k => !activeMetrics.Contains(k)).ToList();
    foreach (var k in stale) { _curLevel.Remove(k); _lastAlarmUtc.Remove(k); }
}
```

### [Medium] PerfSeries.Snapshot/Last 中非空断言 `!` 依赖 T 为 struct 的隐式保证

**文件**：PerfSeries.cs 行 51、68
**类型**：类型约束不足 + NRE 隐患（未来泛型参数改为引用类型时静默崩溃）
**触发**：当前所有使用点（PerfPoint、RequestTiming）都是 struct（不可 null），`default(T?)` 是 `null`（可空 struct）但经过 `_buf[(start + i) % _capacity]!` 断言后变成 default struct（非 null）。如果未来 PerfSeries 用于引用类型（如 `PerfSeries<string>`），空槽位会被当作实际数据返回。

**代码片段**：

```csharp
public T[] Snapshot()
{
    lock (_gate)
    {
        var result = new T[_count];
        int start = _count < _capacity ? 0 : _head;
        for (int i = 0; i < _count; i++)
            result[i] = _buf[(start + i) % _capacity]!; // ← 非空断言依赖当前场景
        return result;
    }
}
```

**实际评估**：当前类型使用都是 struct，default 不是 null，`!` 只是绕过编译器警告。但设计意图（环形缓冲永远满时才读取，未满时只返回有效 count 内的元素）本身正确。真正的风险是如果未来某刻 `Add(null)` 被调用（引用类型），不会被拦截。

**修复建议**：添加类型约束 `where T : struct`，明确意图。如果需要也支持引用类型，把返回类型改为 `T?[]`。

### [Medium] PerfSampler.Dispose 中 `_slowGate.Dispose()` 与 `SampleSlowAsync` 可能存在的竞态

**文件**：PerfSampler.cs 行 334–345（Dispose）、行 175–253（SampleSlowAsync）
**类型**：资源释放顺序
**触发**：Dispose 时 SampleSlowAsync 正在执行（已 acquired 信号量但尚未到 Release 的 finally 块）。

**代码片段**：

```csharp
// Dispose 顺序：
_disposed = true;    // 1. 新 tick 早退
Stop();              // 2. Timer 停止
lock (_gate) { _monitor?.Dispose(); _monitor = null; } // 3. monitor 释放
_slowGate.Dispose(); // 4. ← 如果 SampleSlowAsync 还在 await / metrics.GetVramTextAsync / mon.CaptureSnapshotAsync 中，尚未 Release → Dispose 后 Release 抛 ObjectDisposedException 被 catch？
_timer.Dispose();    // 5. Timer 释放
```

MSDN：`SemaphoreSlim.Dispose()` "Releases all resources used by the current instance of the SemaphoreSlim class."。Dispose 后调用 `Release()` 会抛 ObjectDisposedException，但 SampleSlowAsync 的 finally 块 `if (acquired) _slowGate.Release();` 如果 acquired=true 会抛异常被 Dispose 线程吞掉。**不影响功能**（Dispose 后没人再 WaitAsync），但 finally 中的异常会逃逸到 AsyncMethodBuilder 中观察到。

**实际风险**：低。Timer 已 Stop 不会有新 tick 触发 SampleSlowAsync，但正在执行的那轮可能还没 Release。Dispose 时让已 acquired 的等待者释放一个已 Dispose 的信号量会抛 ObjectDisposedException，这个异常会在 async 状态机中被观察到（可能写进 ETW 日志或未被捕获导致进程崩溃）。

**修复建议**：Dispose 前先 Wait 让 inflight 的 SampleSlowAsync 自然结束（加一个 `_pendingSlow` 计数字段配合 Interlocked），或把 _slowGate.Dispose() 移到最后并把 Release 包裹 try-catch。

### [Medium] RequestTimingTracker.Complete 中 TicksPerMs 除法精度损失

**文件**：RequestTimingTracker.cs 行 17、行 87–90
**类型**：数值精度
**代码片段**：

```csharp
private static readonly double TicksPerMs = Stopwatch.Frequency / 1000.0;
...
WakeWaitMs = wake / TicksPerMs,      // long / double → double
GatewayMs = gateway / TicksPerMs,
BackendMs = backend / TicksPerMs,
TotalMs = total / TicksPerMs,
```

Stopwatch.Frequency 在 Windows 上通常是 10_000_000（10 MHz），TicksPerMs = 10_000。除法是整数 ÷ 整数再转 double 除法（因为 TicksPerMs 是 double）。`wake / 10000.0` 对 10 MHz 时钟是精确的——每个 tick 正好 0.1μs。对大多数硬件来说精度完全足够。

**降级判断**：TickPerMs 的 double 除法精度对秒级时延测量（`GatewayMs` 等字段是 double）来说远超需求（误差 < 10ns）。**降级为 Low**。

### [Medium] MonotonicClock.EpochLocal 在类型首次加载时固定，与 Stopwatch.EpochStopwatch 存在微秒级对齐误差

**文件**：MonotonicClock.cs 行 12–13
**类型**：时间基准精度
**代码片段**：

```csharp
private static readonly DateTime EpochLocal = DateTime.Now;
private static readonly long EpochStopwatch = Stopwatch.GetTimestamp();
```

`DateTime.Now` 和 `Stopwatch.GetTimestamp()` 是两次独立调用，存在微秒级时间差。`Now() = EpochLocal + (Stopwatch.Now - EpochStopwatch)` 这个合成方式会把启动瞬间的微秒误差固化到所有采样点上——但因为所有采样点共享同一个基准，采样点之间的时间差是用 `Stopwatch` 差值计算的（准确的），epoch 偏移只影响绝对值显示。

**后果**：PerfLog 写的时间戳（来自 PerfPoint.Ts = MonotonicClock.Now()）与 PerfLog 自己用 `DateTime.Now` 写的时间戳不一致——PerfLog.WriteLine（行 146）写日志时间用的是 `DateTime.Now`，而 LogSystem/LogCpp 中 PerfPoint.Ts 如果写进 payload（目前没写）会用 MonotonicClock 时间。**目前 PerfLog 没有把 PerfPoint.Ts 写入 payload，只写 DateTime.Now 行首时间戳**——OK，两者在同一机器上差异极小。

**实际风险**：当前无直接冲突。降级为 Low。

## 观察 / 防御建议

### [Observation] PerfAnalyzer.ParsePerfLog 对 `DateTime.TryParse` 的依赖隐含 perf.log 时区一致性假设

PerfLog.WriteLine 写的是本地时间 `DateTime.Now.ToString("yyyy-MM-dd HH:mm:ss.fff")`。PerfAnalyzer.ParsePerfLog 用 `DateTime.TryParse` 解析——在同一台机器上写入和读取时区一致，没问题。但如果 perf.log 被跨时区迁移（如从开发机搬到服务器分析），解析结果会因 CultureInfo.CurrentCulture 时区不同而有偏差。

PerfLog 应考虑写 UTC 时间戳（配合 PerfPoint.Ts 已经是单调时钟、PerfLog 自己用本地时间的不一致）。

### [Observation] PerfSampler.SampleSlowAsync 中 _metrics.GetVramTextAsync 和 mon.CaptureSnapshotAsync 无超时保护

`SemaphoreSlim.WaitAsync(0)` 只保护了不重叠，但一旦进入慢采集后，如果 nvidia-smi 挂住或后端 endpoint 无响应（比如后端正在重启、TCP 半开连接），整个慢采集循环会卡住**直到 async 超时或被 Dispose 打断**。建议给 `GetVramTextAsync` 和 `CaptureSnapshotAsync` 各自加 CancellationTokenSource 超时。

### [Observation] RequestTimingTracker._open 字典无容量上限——异常 Complete 未调用会长期占用

Begin 调用后如果 Complete 永远不调用（网关层 crash、客户端直接 RST），_open 中的 OpenEntry 永远不会被 Remove。在长期运行场景下，每次请求不 Complete 就会泄漏一个 OpenEntry（~100 bytes）。

建议添加"超时回收"后台任务：定期扫描 _open 中 TRecv 超过 N 秒的条目并清理，标记为 incomplete（不计入统计但释放内存）。

### [Observation] MetricKeys 作为"唯一权威注册表"但 All 列表不包含事件型指标的 op 值（kv_save / kv_restore / slot_select / wakeup 等）

MetricKeys 的分层声明只覆盖了采样点指标（PerfPoint 字段）和请求级指标，事件型 op 值（PerfEvent.Category + PerfEvent.Op 组合）散落在注释和代码中无集中定义。如果需要在 PerfThresholdRule 或监控页显示中覆盖事件指标，会导致新的命名漂移。

建议：为 PerfEvent.Category 和 PerfEvent.Op 也建立常量注册表，或在 MetricKeys 下新增事件型指标分组。
