### [Medium] LogPipeline.Shutdown 与并发 Enqueue 存在窗口竞态导致消息静默丢失

**文件**：LogPipeline.cs 行 324–332（Enqueue）、行 446–464（Shutdown）
**类型**：并发竞态（竞态窗口小，日志尽力而为语义下降级）
**触发**：Shutdown() 设置 `_accepting = false` 后立刻唤醒写线程 Join；同时 Enqueue 线程已进入 `lock(_enqueueGate)` 并通过了 `if (!_accepting)` 检查但尚未 `TryEnqueue`。此时写线程被唤醒，Drain 时该消息尚未入队，若队列刚好空则写线程退出，后续 Enqueue 才 TryEnqueue 但已无人消费。

**证据链三要素**：

1. Enqueue 结构：`lock(_enqueueGate) → 读 _accepting → 构造 msg → TryEnqueue(获取 BoundedLineQueue._gate)` —— 两次独立加锁，中间窗口存在。
2. Shutdown 结构：`_accepting = false`（volatile 写，无锁） → `_wake.Set()` → `Join(_joinTimeoutMs)` —— 写线程被唤醒后立即执行 `Drain → 检查 _queue.Count == 0 → break`。
3. 竞态序列：
   ```
   Enqueue 线程 A  : lock(_enqueueGate), 读 _accepting=true, 构造 msg...
   Shutdown 线程   : _accepting=false, Set _wake, Join
   Writer 线程     : Wait 返回, Drain 空队列, _shutdownRequested && Count==0 → break, 退出
   Shutdown 线程   : Join 成功, DisposeWriters
   Enqueue 线程 A  : 此时才 TryEnqueue，但写线程已退出 → 消息入队后无人消费
   ```

**后果**：关闭阶段的最后若干条日志消息静默丢失（队列中没有）。由于日志本身是尽力而为设计，此问题影响有限，但在异常退出场景下会丢失可能关键的错误日志。

**建议**：Shutdown 进入前先获取 `_enqueueGate` 短暂持有后再释放，确保没有 Enqueue 正在进行；或让写线程在 Drain 循环外再做一次 `_queue.TakeAll` drain。

```csharp
// 现状（有竞态窗口）：
_accepting = false;
_shutdownRequested = true;
_wake.Set();
bool joined = _writerThread.Join(_joinTimeoutMs);
```

### [Medium] PerfLog.Start 中 RotateLocked 后叠加 OpenWriter 导致句柄延迟释放

**文件**：PerfLog.cs 行 29–40（Start）、行 161–187（RotateLocked）
**类型**：资源泄漏（延迟释放，GC finalizer 兜底）
**触发**：perf.log 已超限（_bytes >= MaxFileBytes）时调用 Start()。

**代码片段**：

```csharp
// PerfLog.Start 行 37-38：
if (_bytes >= MaxFileBytes) RotateLocked();  // RotateLocked 内部已 _writer = OpenWriter(...)
_writer = OpenWriter(path);                   // ← 覆盖了 RotateLocked 新开的 writer，未 Dispose
```

RotateLocked 末尾（行 179-180）：
```csharp
_writer = OpenWriter(basePath);  // 第一次打开
_bytes = 0;
```

Start 行 38 紧接着又打开：
```csharp
_writer = OpenWriter(path);      // 第二次打开（文件已被 RotateLocked Move，此时不存在，新建空文件）
```

**后果**：RotateLocked 内创建的 StreamWriter 被覆盖引用后延迟释放（依赖 GC finalizer），窗口很小（仅启动时文件恰好满才触发），但句柄未显式 Dispose 违反确定性资源管理原则。

**建议**：Start 中 RotateLocked 后不再 OpenWriter：
```csharp
if (_bytes >= MaxFileBytes) RotateLocked();
else _writer = OpenWriter(path);
```

### [Medium] PerfLog.Escape 缺失对反斜杠转义；字段值中的反斜杠会污染下一行解析

**文件**：PerfLog.cs 行 199
**类型**：数据格式健壮性
**触发**：请求 path 包含反斜杠（Windows 绝对路径如 `C:\Users\...`）或 app 名含反斜杠时。

**代码片段**：

```csharp
private static string Escape(string v) => v.Replace(',', ' ').Replace('\n', ' ').Replace('\r', ' ');
```

解析端（PerfAnalyzer.ParseKeyValues 行 607–617）：
```csharp
var kv = new Dictionary<string, string>(StringComparer.OrdinalIgnoreCase);
for (int i = start; i < parts.Length; i++)
{
    var eq = parts[i].IndexOf('=');
    if (eq <= 0) continue;
    kv[parts[i].Substring(0, eq)] = parts[i].Substring(eq + 1);
}
```

**后果**：反斜杠不影响逗号分割（因为逗号已替换），但值内反斜杠本身不是解析问题源。真正的问题是 `Escape` 替换逗号为空格但不替换双引号或等号——如果 path 含 `=`，会导致解析端 `IndexOf('=')` 定位错误。不过 `PerfLog.LogTiming` 中 `sb.Append(",path=").Append(Escape(t.Path))`，如果 path 本身含 `=`（极罕见），`parts[i]` 变成 `path=a=b=c`，`IndexOf('=')` 取第一个，值为 `a=b=c`——这其实是 OK 的。

**降级判断**：原想升级为 [Medium]，但实际分析后 Escape 已覆盖逗号/newline/carriage return 三大解析破坏源，等号出现在值内时 `IndexOf('=')` 取第一个正好正确。降为 Low。

### [Medium] AppConfig.Sanitize 对字符串字段（路径/端口/掩码）无格式校验，异常值直通

**文件**：AppConfig.cs 行 181–203
**类型**：输入校验缺失
**触发**：config.json 中 `ExePath` 为空但非空字符串（只含空格）、`PCoreMask` 格式非法、`AutoPreemptiveApps` 为空字符串、`KvCachePath` 含非法路径字符等。

**代码片段**：

```csharp
public static void Sanitize(AppConfig cfg)
{
    if (cfg.Port is < 1 or > 65534) cfg.Port = 8080;
    // ... 仅数值字段 ...
    // 字符串字段无校验：ExePath / ModelPath / PCoreMask / AutoPreemptiveApps / AutoSnapshotKeys / ExtraArgs / LoadMode / CacheTypeKv / SpecType
}
```

**后果**：异常配置值传递到下游（如 SmartScheduler.CommandLine 拼接、SlotAffinity 指纹匹配），可能导致运行时启动失败（空 ExePath）、异常日志刷屏（非法 PCoreMask 被传给 SetProcessAffinityMask 失败重试）、或静默降级（非法路径在 File.Move 时抛异常被 catch）。

**建议**：Sanitize 中补充字符串字段校验：ExePath 非空且不含空字符、PCoreMask 匹配 `^0x[0-9A-Fa-f]+$`、AutoPreemptiveApps 逗号分隔每项非空。

### [Medium] TokenGuard.GuardAsync 裁剪截断可能切断 surrogate pair 产生无效 UTF-16

**文件**：TokenGuard.cs 行 162–179（内容兜底二分收敛）、行 173–174（截断逻辑）
**类型**：Unicode 边界安全
**触发**：单条消息内容含 emoji（多 surrogate pair）且恰好截断在 pair 中间位置。

**代码片段**：

```csharp
// 行 170-174
int half = newLen / 2;
int tail = newLen - half;
string kept = content[..half] + "\n[…]\n" + content[^tail..];
SetContent(messages[maxIdx]!, kept + "\n[已截断 - Token Guard]");
```

`content.Length` 返回 char 数（UTF-16 code unit 数）。如果 `half` 恰好落在 high surrogate 位置（`\uD800`–`\uDBFF` 范围），`content[..half]` 会留下不完整的 high surrogate，后续 JSON 序列化时 System.Text.Json 会用 `\uFFFD` 替换，可能导致 token 计数偏差（被替换字符长度 ≠ 原 pair）。

**后果**：截断后 JSON 序列化的字符数与 EstimateTokensByChars 估算不一致——可能导致裁剪后的 count 与估算偏差，极端情况下仍超预算返回 false。但 EstimateTokensByChars 是保守估算（宁多裁），实际影响有限。

**建议**：截断前检测 `content[half - 1]` 是否为 high surrogate，若则前移 1 位。或改用 `StringInfo.SubstringByTextElements` 按 code point 截断。

### [Medium] LogPipeline._consecutiveIoFailures 计数器类型为 int 但单线程写线程安全；ProcessOne catch 中连续递增无初始重置

**文件**：LogPipeline.cs 行 278、行 383–401
**类型**：无界增长（低风险）
**触发**：长时间磁盘 IO 异常 + 间歇性成功场景下 _consecutiveIoFailures 反复归零后递增，上限 3 不会溢出；但注释说"连续失败退避"实际阈值硬编码 3，无配置化。

**实际上**：这是低风险的——`_consecutiveIoFailures` 在每次 ProcessOne 成功时归零（行 393 `_consecutiveIoFailures = 0;`），只有在持续 IO 失败时才连续递增，触发 Sleep(200) 后仍归零。不存在无界增长。**降级为 Low**。

**代码片段**：

```csharp
catch
{
    Interlocked.Increment(ref _ioFailCount);
    if (++_consecutiveIoFailures >= 3) Thread.Sleep(200);
}
```

### [Low] AppConfig.Save 用 overwrite: true 原子重命名，但 tmp 文件名无冲突防护（多实例同时 Save）

**文件**：AppConfig.cs 行 251–267
**类型**：原子性边界
**触发**：两个 harness 进程同时 Save 同一 config.json。

**代码片段**：
```csharp
var tmp = ConfigPath + ".tmp";
File.WriteAllText(tmp, ...);
File.Move(tmp, ConfigPath, overwrite: true);
```

两个进程都写同名 .tmp 文件 → 后写覆盖前写；后 Move 覆盖先 Move。结果是**最后一次写入获胜**，不损坏文件但可能丢失一个进程的配置。

**后果**：多实例共享同目录时配置静默丢失。实际场景一般单实例运行，风险低。

## 观察 / 防御建议

### [Observation] TokenGuard 对超长 BuildMessagesText 无内存上限保护

`BuildMessagesText` 会把全部 messages 拼成一个 string 送 tokenize。如果请求体含巨型 tool_result（数 MB），拼接后的字符串会占据大量 GC 堆，同时 `CountTokensAsync` 还会序列化 + HTTP 传输 + 反序列化。建议在 MeasureAsync 入口做前置检查：`root["messages"].Count` > 阈值或总字符数 > 阈值时跳过计量日志、直接走 GuardAsync 裁剪路径。

### [Observation] LogFile._recent Queue 与 LogPipeline._warnContext 语义重复

LogFile._recent（生产侧，最近 10 条）与 LogPipeline._warnContext（写线程侧，最近 10 条）都缓存"该条之前 N 条"上下文，但各自独立维护、更新时机不同（生产侧 Enqueue 成功即更新 vs 写线程 ProcessOne 时更新）。生产侧 _recent 会受丢弃影响（Enqueue 失败不更新），写线程侧不受丢弃影响。两者存在轻微的语义错位。建议统一为一处维护：要么把 _recent 移到 LogPipeline 由写线程维护并暴露 ReadOnlyList，要么反过来 LogPipeline 从 LogFile 读——但前者会破坏 LogFile 作为生产侧"零锁返回"的契约。当前设计是合理的权衡。
