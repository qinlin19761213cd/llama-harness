### [High] SystemMetrics.GetCpuPercent 多线程并发读写无保护，采样值错乱

- **文件行号**: [SystemMetrics.cs:43-64](file:///C:/project/lunch/LlamaHarness/SystemMetrics.cs#L43-L64)
- **类型**: 并发竞态 / 数据损坏
- **触发**: UI 中多个独立组件（如性能面板、系统监控 Widget）同时注册定时采样调用 `GetCpuPercent()`，或采样定时器间隔极短（<100ms）时，`_prevIdle`/`_prevKernel`/`_prevUser`/`_hasSample` 四个字段被无锁读写
- **后果**: uint 差值基于半更新状态（例如 `_prevIdle` 已写入新值但 `_prevKernel` 还是旧值），计算出的 `busy`/`total` 差数被严重扭曲——CPU 占用率跳变到 0% 或 200%+，或长期卡在某个错误值。`double pct` 本身的读写不是原子操作，但这里主要的竞态是四个 ulong 字段的半更新。
- **证据链三要素**: (1) 触发源——`GetCpuPercent()` 是公开实例方法，无 `[MethodImpl(MethodImplOptions.Synchronized)]`、无 lock、无 volatile；(2) 缺陷——字段非原子更新；(3) 可观察后果——CPU 百分比在高并发采样下明显失真。

```csharp
private ulong _prevIdle, _prevKernel, _prevUser;
private bool _hasSample;

public double GetCpuPercent()
{
    // 无锁读取 _prevIdle/_prevKernel/_prevUser
    ulong i = ToU64(idle), k = ToU64(kernel), u = ToU64(user);
    double pct = 0;
    if (_hasSample)
    {
        ulong idleDelta = i - _prevIdle;         // 可能读到半更新
        ulong kernelDelta = k - _prevKernel;
        ulong userDelta = u - _prevUser;
        ulong busy = (kernelDelta > idleDelta ? kernelDelta - idleDelta : 0) + userDelta;
        ulong total = busy + idleDelta;
        pct = total > 0 ? 100.0 * busy / total : 0;
    }
    // 无锁写回
    _prevIdle = i; _prevKernel = k; _prevUser = u; _hasSample = true;
    return pct;
}
```

- **修复建议**: 在方法体加 `lock (_gate)`，或用 `Interlocked` 系列分别保护每个字段（但跨字段一致性需要锁）。也可以在文档中声明"单线程访问"——但既然公开，就应线程安全。

### [High] LlamaCppMonitorCollector 三个 Linked CancellationTokenSource 未 Dispose，句柄泄漏

- **文件行号**: [LlamaCppMonitor.cs:111-113](file:///C:/project/lunch/LlamaHarness/LlamaCppMonitor.cs#L111-L113)
- **类型**: 资源泄漏（P0-H-05 修复的遗漏）
- **触发**: 每次调用 `CaptureSnapshotAsync()` 都会创建 3 个 `CancellationTokenSource.CreateLinkedTokenSource`，但这些 CTS 没有被 `using` 包裹，也没有显式 Dispose
- **后果**: CTS 内部持有内核事件句柄（ManualResetEvent）。`CreateLinkedTokenSource` 会注册回调到父 CTS。当 timeoutCts 被 `using` 释放后，slotsCts/propsCts/metricsCts 仍有回调挂在 timeoutCts.Token 上，直到 GC 才会清理。高频调用 Monitor（如未来改成自动轮询）时句柄缓慢堆积。即使单次调用也会造成 GC 压力。
- **证据链三要素**: (1) 触发源——`CaptureSnapshotAsync` 每次调用必然创建 3 个 CTS；(2) 缺陷——无 Dispose；(3) 可观察后果——进程句柄数在多次调用后持续增长，直到 GC 触发终结器。

```csharp
// P0-H-05 修复注释说"避免共享 CTS 导致连带取消"——确实修了连带取消，但忘了 Dispose 这三个 CTS
var slotsCts = CancellationTokenSource.CreateLinkedTokenSource(timeoutCts.Token);
var propsCts = CancellationTokenSource.CreateLinkedTokenSource(timeoutCts.Token);
var metricsCts = CancellationTokenSource.CreateLinkedTokenSource(timeoutCts.Token);
// ← 这三个都没有 using，也没有在方法尾部 Dispose
```

- **修复建议**: 三个 CTS 全部改用 `using var` 声明，或在 finally 块里 Dispose。

- **文件行号**: [LlamaStatsParser.cs:117-121](file:///C:/project/lunch/LlamaHarness/LlamaStatsParser.cs#L117-L121)

    RoundUpdated?.Invoke(round);   // 锁外触发——round 可能在其他 Feed 中继续被改

- **修复建议**: 要么把 RoundStats 改成每次事件触发前做快照，要么在 RoundStats 字段声明上加 `Volatile` 写入/读取。

### [Medium] LlamaServerClient.GetMetricsAsync / GetJsonAsync catch-all 吞没 OperationCanceledException

- **文件行号**: [LlamaServerClient.cs:171-183](file:///C:/project/lunch/LlamaHarness/LlamaServerClient.cs#L171-L183), [LlamaServerClient.cs:192-205](file:///C:/project/lunch/LlamaHarness/LlamaServerClient.cs#L192-L205)
- **类型**: 异常语义丢失
- **触发**: 调用方传入的 `CancellationToken ct` 在请求进行中被取消时（如停机、窗口关闭、调用方主动取消），HttpClient 会抛 `OperationCanceledException`，但被 catch-all 吞掉，返回 null
- **后果**: 调用方无法区分"后端真的返回非 2xx"和"请求被外部取消"。对于 `LlamaCppMonitorCollector.CaptureSnapshotAsync`，会把取消当成采集失败，丢失了主动停止的语义。
- **代码片段**:

```csharp

{
    try
    {
        using var resp = await _http.GetAsync(...);
        if (!resp.IsSuccessStatusCode) return null;
        return await resp.Content.ReadAsStringAsync(ct);
    }
    catch
    {
        return null;  // ← 把 OperationCanceledException 也吞了
    }
}
```

- **修复建议**: `catch (OperationCanceledException) { throw; }` + `catch { return null; }`。

### [Medium] OutputContinuer 整条流式管道无 CancellationToken 贯穿，客户端断开后仍在循环续接

- **文件行号**: [OutputContinuer.cs:41-45](file:///C:/project/lunch/LlamaHarness/OutputContinuer.cs#L41-L45), [OutputContinuer.cs:64-138](file:///C:/project/lunch/LlamaHarness/OutputContinuer.cs#L64-L138)
- **类型**: 无取消通路 / 资源浪费
- **触发**: `HandleStreamAsync` 和 `PipeLoop` 方法签名中没有 CancellationToken。循环续接时（最多 `cfg.MaxContinuations` 轮），即使客户端已经断开连接、`outResp` 已不可用，循环仍会继续跑，发起后续续接请求
- **后果**: 后端资源被白白占用，keep-alive task 循环还在尝试写已断开的流（虽然会被 catch 吞掉）。如果 MaxContinuations=5 且后端每轮都截断，总共 5 轮请求 + 中间 keep-alive 持续跑，浪费后端连接和内存。
- **代码片段**:

```csharp
// 入口完全没有 CancellationToken 参数
public static Task<(bool Completed, string Accumulated)> HandleStreamAsync(
    IBackendClient backend, Uri uri, string originalBody,
    HttpResponseMessage firstResp, HttpListenerResponse outResp,
    AppConfig cfg, Action<string>? log, Func<Task>? onTruncation = null)
    => PipeLoop(...);

private static async Task<(bool Completed, string Accumulated)> PipeLoop(
    IBackendClient backend, Uri uri, string originalBody,
    HttpResponseMessage firstResp, HttpListenerResponse outResp,
    AppConfig cfg, Action<string>? log, SemaphoreSlim? writeGate = null,
    Func<Task>? onTruncation = null)
{
    // while(true) 续接循环——没有取消检查
    while (true) { ... }
}
```

- **修复建议**: 所有 Handle*/Pipe* 方法签名增加 `CancellationToken ct = default`，在 while 循环每轮开头加 `ct.ThrowIfCancellationRequested()`，续接请求的 `backend.SendAsync` 传入 ct。

### [Medium] LlamaServerClient.SendAsync 首字节超时看门狗用 CancellationToken.None，外部取消后看门狗仍跑满 timeout

- **文件行号**: [LlamaServerClient.cs:65-79](file:///C:/project/lunch/LlamaHarness/LlamaServerClient.cs#L65-L79)
- **类型**: 资源浪费 + 取消语义不对称
- **触发**: 调用方传入的 `ct` 被 `CreateLinkedTokenSource` 链接后传给 `_http.SendAsync`，但 `Task.Delay(TimeSpan.FromSeconds(timeout), CancellationToken.None)` 用的是 `CancellationToken.None`——即使外部取消，delayTask 仍会等满 `timeout` 秒才结束
- **后果**: 当外部 ct 先取消（例如整个应用停机），sendTask 被 linkedCts 取消后很快收敛，但 delayTask 还在后台等。虽然 `Task.WhenAny` 已经等 sendTask 了，函数会早返回，但 delayTask 继续挂着浪费一个 Timer 资源直到 timeout。在批量请求停机场景下，可能有 N 个 Timer 同时跑满 timeout。
- **代码片段**:

```csharp
using var linkedCts = CancellationTokenSource.CreateLinkedTokenSource(ct);
linkedCts.CancelAfter(TimeSpan.FromSeconds(timeout));

var sendTask = _http.SendAsync(request, option, linkedCts.Token);
var delayTask = Task.Delay(TimeSpan.FromSeconds(timeout), CancellationToken.None); // ← 不用 ct
```

- **修复建议**: `Task.Delay(TimeSpan.FromSeconds(timeout), ct)` 或 `Task.Delay(TimeSpan.FromSeconds(timeout), linkedCts.Token)`——让看门狗也能被外部取消。

### [Low] MonotonicClock.EpochLocal 用 DateTime.Now（本地时区），跨时区/夏令时切换可能导致比较混乱

- **文件行号**: [MonotonicClock.cs:12](file:///C:/project/lunch/LlamaHarness/MonotonicClock.cs#L12)
- **类型**: 时间基准一致性
- **触发**: 进程在夏令时切换期间运行（Windows 自动更新时区），或系统时区被手动更改
- **后果**: `EpochLocal` 是固定值（类型初始化时快照），后续用 `AddMilliseconds` 加单调偏移。理论上不会"倒挂"（因为单调偏移始终增加），但 `Now()` 返回的 `DateTime` 的 `.Kind` 是 `DateTimeKind.Local`，与 UTC 时间戳混合比较时可能产生 8 小时偏差。
- **修复建议**: 把 `EpochLocal` 改成 `EpochUtc` = `DateTime.UtcNow`，返回值 `.ToLocalTime()` 给 UI 显示；或者保持 Local 但文档明确标注"本地时区基准"。

### [Low] LlamaFinder.BuildArgs ExtraArgs 白名单过滤后整体加 args，多个参数会被当成一个 token

- **文件行号**: [LlamaFinder.cs:168-177](file:///C:/project/lunch/LlamaHarness/LlamaFinder.cs#L168-L177)
- **类型**: 参数解析语义
- **触发**: 用户在 ExtraArgs 里写 `--param1 val1 --param2 val2`（含空格），白名单过滤后字符串保持不变，`args.Add(extra)` 整体作为一个字符串加入
- **后果**: `string.Join(" ", args)` 后确实会变成 `"--param1 val1 --param2 val2"` 这样的命令行，Windows 会按空格切分为独立 token 传给 llama-server——实际上是对的！因为 Windows CreateProcess 会把 Arguments 字符串整体交给子进程命令行解析。所以这**不是 bug**，只是设计上依赖"最终 Join 后被 CreateProcess 正确切分"
- **实际风险**: 如果 ExtraArgs 里有转义的引号 `\"`（不在白名单里会被剔除），反而会让用户困惑"为什么我加了引号不生效"。这是白名单的 trade-off，需要文档说明。

### [Observation] MonotonicClock 在 Stopwatch 精度不足的平台（极罕见）上可能出现同一毫秒内多次 Now() 返回相同值

- **文件行号**: [MonotonicClock.cs:14-18](file:///C:/project/lunch/LlamaHarness/MonotonicClock.cs#L14-L18)
- **说明**: `TicksPerMs` 用 `(double)Stopwatch.Frequency / 1000.0`，在 Windows 上 Stopwatch.Frequency 固定 10MHz（100ns 分辨率），远高于 1ms。除法结果 `(stopwatchDelta / TicksPerMs)` 截断到 long 毫秒，所以快速连续调用（<1ms）会得到相同时间戳。对于需要精确排序的场景（如采样点），可考虑返回 `long` 毫秒偏移 + 高位 tick 补充。
