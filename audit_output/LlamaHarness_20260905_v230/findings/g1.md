### [中] TryRecoverContextOverflowAsync 重发失败路径未关闭 ctx.Response，导致 HttpListener 连接泄漏
- **文件:行号**：`SmartScheduler.Pipeline.cs:L217-L222`（裁剪失败路径）、`SmartScheduler.Pipeline.cs:L268-L279`（重发仍失败路径）
- **类型**：资源泄漏
- **触发**：400 上下文超限自愈分支命中；aggressive trim 失败或重发后仍返回非 2xx 状态码
- **后果**：HttpListenerContext.Response 的 OutputStream 未 Close。在长运行网关进程中，积累后可能耗尽端口或连接资源，导致 HttpListener 后续 `GetContextAsync` 异常。`PumpResponseAsync` 的 finally 块负责 Close，但这两条 return true 的路径直接跳过了 `PumpResponseAsync`，而自身只调用了 `OutputStream.WriteAsync` 未调 `Close`。
- **代码片段**：

```csharp
// Pipeline.cs L217-222（裁剪失败）
outResp.StatusCode = 400;
outResp.ContentType = "application/json";
var bytes = System.Text.Encoding.UTF8.GetBytes(errBody);
outResp.ContentLength64 = bytes.Length;
await outResp.OutputStream.WriteAsync(bytes);
return true; // ← 未 Close，PumpResponseAsync 被跳过

// Pipeline.cs L274-279（重发仍失败）
outResp.ContentType = "application/json";
var bytes2 = System.Text.Encoding.UTF8.GetBytes(retryErr);
outResp.ContentLength64 = bytes2.Length;
await outResp.OutputStream.WriteAsync(bytes2);
Log?.Invoke($"[TOKEN-GUARD-FATAL] 400 自愈重发仍失败（{(int)retryResp.StatusCode}）");
return true; // ← 未 Close
```

**修复建议**：在两处 return true 前补 `outResp.Close()`，或把 Close 下沉到 `SendAndPipeAsync` 的统一 finally 中。

### [中] HandleHealth 同步阻塞 `.GetAwaiter().GetResult()`，未来 UI 线程调用会死锁
- **文件:行号**：`SmartScheduler.Http.cs:L255`
- **类型**：并发 / 潜在死锁
- **触发**：当前路径（AcceptLoopAsync → HandleRequestAsync → HandleHealth）在线程池，`Task.Run(AcceptLoopAsync)` 启动时无同步上下文所以安全。但 `HandleHealth` 是 public 可被外部直接调用，若未来被 UI 线程（WinForms）或 ASP.NET SynchronizationContext 线程直接调用，HttpClient 内 await 会尝试回到原同步上下文形成死锁。
- **后果**：UI 假死 / 请求永久挂起。现有代码虽然没直接证据但属于已知反模式。
- **代码片段**：

```csharp
// Http.cs L255
RequestProcessor.WriteJsonAsync(ctx, 200, json).GetAwaiter().GetResult();
return true;
```

**修复建议**：把 `HandleHealth` 改为 `async Task<bool>`，调用方 `await`。当前所有调用点（`HandleRequestAsync`）已是 async，改动零摩擦。

### [中] Handler 看门狗超时后 handlerTask 继续跑，可能访问已写入/关闭的 ctx.Response
- **文件:行号**：`SmartScheduler.Http.cs:L365-L413`
- **类型**：并发 / 竞态
- **触发**：`handlerCts` 300 秒到期 → 看门狗先到 → 写 504 → handlerTask 继续后台执行 → 到达 `ForwardAsync` 写回 `ctx.Response` → 该 ctx 在 finally 已被 Close
- **后果**：`ObjectDisposedException` / `IOException` 写已关闭流，虽然会被 catch 吞掉，但在大流量下会产生大量噪音日志。注释已承认"不改变下游任务执行"是已知折中，风险可控。
- **代码片段**：

```csharp
// Http.cs L406-L412
else
{
    handlerCts.Cancel();
    throw new TimeoutException($"请求处理超时（>{HandlerTimeoutSeconds}s）");
}
// handlerTask 继续在后台跑（没有被 Cancel）
```

**修复建议**：Task.Run 闭包内传入 CancellationToken，让 `EnsureRunningAsync` / `ForwardAsync` / `PumpResponseAsync` 等各阶段在入口处检查 `ct.IsCancellationRequested` 后提前退出。

### [低] SetPhase 存在 TOCTOU 竞态，并发 SetPhase 可能触发多次 PhaseChanged
- **文件:行号**：`SmartScheduler.Lifecycle.cs:L561-L565`
- **类型**：并发
- **触发**：WakeUpAsync 置 Phase.Running 与 StopNow 置 Phase.Standby 同时发生（如用户手动停止恰好赶上唤醒成功）
- **后果**：PhaseChanged 被多播两次（先 Running 后 Standby），事件消费者（UI/监控）可能短暂闪烁。最终 `_phase` 写入正确（后写覆盖），无持久损坏。
- **代码片段**：

```csharp
int oldPhase = Volatile.Read(ref _phase);
if ((Phase)oldPhase == p) return;
Volatile.Write(ref _phase, (int)p);
PhaseChanged?.Invoke(p);
```

**修复建议**：改用 `Interlocked.CompareExchange` 单次完成"比较+写入"，只有 CAS 成功才 Invoke。

### [低] ParseAutoPreemptivePrefixes / ParseAutoSnapshotPrefixes 在热路径每次请求重建 List
- **文件:行号**：`SmartScheduler.Gateway.cs:L330-L334`（ParseAutoPreemptivePrefixes）、`Gateway.cs:L343-L347`（ParseAutoSnapshotPrefixes）
- **类型**：性能
- **触发**：每个推理请求进入 `ApplySlotAffinityAsync` → 调用 `ParseAutoPreemptivePrefixes()` 都会执行一次 `Split + Select + Where + ToList()`，产生临时数组 + List + 字符串分配
- **后果**：高并发下增加 GC 压力（Gen0 频率升高）。通常 AutoPreemptiveApps 只有几十条，影响有限，但这是典型可避免的热路径分配。
- **代码片段**：

```csharp
private List<string> ParseAutoPreemptivePrefixes()
{
    return _cfg.AutoPreemptiveApps.Split(',', StringSplitOptions.RemoveEmptyEntries)
        .Select(s => s.Trim()).Where(s => s.Length > 0).ToList();
}
```

**修复建议**：在 `AppConfig` 变更通知或唤醒时解析一次缓存在字段里；或用 `Lazy<List<string>>` + `WeakReference` 等方式降低分配。

### [低] OnServerExited 在运行态被 StopNow 提前置 Phase.Standby 后不会再被触发
- **文件:行号**：`SmartScheduler.Lifecycle.cs:L491-L502`
- **类型**：逻辑
- **触发**：StopNow() L527 先 `SetPhase(Phase.Standby)`，再 `_server.Stop()`；之后进程真正退出时 OnServerExited 被触发，但 p != Sleeping && p != Running → 直接跳过
- **后果**：**无实际破坏**。代码注释已说明这是"修复"行为——避免 Exited 回调重复报告"已退出"日志。但 OnServerExited 的分支条件 `if (p == Phase.Sleeping || p == Phase.Running)` 对 StopNow 场景确实是 dead path。
- **代码片段**：

```csharp
private void OnServerExited(int code)
{
    var p = CurrentPhase;
    if (p == Phase.Sleeping || p == Phase.Running)
    {
        // ...
    }
    // ← p=Standby/Waking 时静默返回
}
```

**说明**：这是防御性设计，不算 bug，但建议加一行注释明确 StopNow 后回调预期被跳过。

### [低] _keepAliveFailures 与 _lastKeepAliveFailLogUtc 跨线程读写缺乏统一锁
- **文件:行号**：`SmartScheduler.Crash.cs:L16-L19, L311-L314`
- **类型**：并发 / 可维护性
- **触发**：多客户端同时触发崩溃恢复 → 各自创建 `RunKeepAliveAsync` → keep-alive 异常时两个线程同时 `Interlocked.Increment` 后竞态写 `_lastKeepAliveFailLogUtc = DateTime.UtcNow`
- **后果**：`_keepAliveFailures` 用了 Interlocked 没问题；但 `_lastKeepAliveFailLogUtc` 的两次写入可能导致节流窗口内日志被意外重置——实际上 CrashRecovery 的三分支互斥（要么 Alive 要么 Restart，不会同时触发多个 RunCrashRecoveryAsync），所以竞态窗口极低。
- **代码片段**：

```csharp
int fails = Interlocked.Increment(ref _keepAliveFailures);
if (DateTime.UtcNow - _lastKeepAliveFailLogUtc > TimeSpan.FromMinutes(1))
{
    _lastKeepAliveFailLogUtc = DateTime.UtcNow;
    log?.Invoke($"[警告] keep-alive 异常（累计 {fails} 次）：{ex.Message}");
}
```

**修复建议**：用 `Interlocked.CompareExchange` 保护 `_lastKeepAliveFailLogUtc` 的时间戳写入，或用一个单独的 `object` 锁。

### [低] IdleMinutes 是 public 可写字段，与 OnTick 读存在撕裂风险（int 在 x86 原子，影响可忽略）
- **文件:行号**：`SmartScheduler.cs:L153`、`SmartScheduler.Lifecycle.cs:L354`
- **类型**：并发 / 可维护性
- **触发**：UI 线程修改 `IdleMinutes` 时，OnTick 恰好读到，理论上 int 在 32/64 位平台都是原子读写，不会撕裂
- **后果**：当前无实际风险。但若未来改为 TimeSpan 或 long 则会撕裂
- **代码片段**：

```csharp
public int IdleMinutes { get; set; } = 15; // SmartScheduler.cs L153
var remaining = new DateTime(lastTouch).Add(TimeSpan.FromMinutes(IdleMinutes)) - DateTime.Now; // Lifecycle.cs L354
```

**建议**：改为 `public int IdleMinutes { get; [MethodImpl(MethodImplOptions.Synchronized)] set; }` 或 `Volatile.Write` setter。

### [低] AcceptLoopAsync 的 Task 未跟踪，Dispose 时无信号让循环优雅退出（依赖 _listener.IsListening 自然断）
- **文件:行号**：`SmartScheduler.Http.cs:L50, L104`
- **类型**：可维护性
- **触发**：Dispose 时 StopListening() 置 `_listener.IsListening=false`，AcceptLoopAsync 内 `while (_listener.IsListening)` 会自然退出
- **后果**：当前机制正确（StopListening → IsListening=false → 下一轮循环退出）。但 Task.Run 返回的 Task 没存字段，没有 await 或 await with timeout，Dispose 时无日志说明仍在运行的 AcceptLoopAsync 被留下。
- **建议**：存到字段，Dispose 时记录状态；或用 `CancellationToken` 贯穿整条管道。

### [观察] WriteErrorV2 / WriteJsonAsync / WriteError 三处错误响应格式不统一
- **文件:行号**：`SmartScheduler.Http.cs:L156-L174 (WriteErrorV2)`、`RequestProcessor.cs:L261-L281 (WriteError)`、`SmartScheduler.Http.cs:HandleHealth` 等多处 WriteJsonAsync
- **类型**：可维护性
- **观察**：`WriteErrorV2` 用嵌套格式 `{"error":{"code":"...","message":"..."}}`，`RequestProcessor.WriteError` 用扁平格式 `{"error":"..."}`。Pipeline.cs 还有 8 处旧格式 WriteError 调用受白名单限制未迁移。新代码（Http.cs/Gateway.cs）统一用 WriteErrorV2，但 Pipeline.cs 用 WriteError，客户端需要同时解析两种格式。
- **建议**：逐步替换 Pipeline.cs 中旧 WriteError 调用为 WriteErrorV2，提供 adapter 签名兼容。

### [观察] PumpResponseAsync finally 中 Close 与 Pipeline.cs TryRecover 分支无 Close 的不对称
- **文件:行号**：`SmartScheduler.Pipeline.cs:L398-L401`、`L217-L222`、`L268-L279`
- **类型**：资源管理一致性
- **观察**：`PumpResponseAsync` 有统一 finally Close；但 `TryRecoverContextOverflowAsync` 的两条 return true 分支没 Close。若未来更多分支在 `SendAndPipeAsync` 里早 return，容易漏 Close。建议把 ctx.Response 关闭责任上收到 `SendAndPipeAsync` 或 `ForwardAsync` 级别的 try-finally。

### [观察] Lazy<IBackendClient> 工厂闭包捕获 `this.Log` — Dispose 后 Lazy 可能被新线程首次访问
- **文件:行号**：`SmartScheduler.cs:L183-L185`、`SmartScheduler.Lifecycle.cs:L551`
- **类型**：可维护性
- **观察**：Dispose 时已 `_backendLazy.IsValueCreated` 才 Dispose。若 Dispose 发生时刚好有并发线程首次访问 Backend（IsValueCreated=false），则 Lazy 工厂会执行，创建新 LlamaServerClient 但永远不会被 Dispose。窗口极窄（Dispose 与首次访问的竞态）。
- **建议**：在 Dispose 前用一个 flag（`_stopRequested` 已经够用）先检查，防止 Lazy 工厂在 Dispose 过程中被触发。

### [观察] OnServerExited、VerifyVramReleasedAsync 等内部方法由 Event / fire-and-forget Task 触发，无异常处理日志兜底
- **文件:行号**：`SmartScheduler.Lifecycle.cs:L505-L519` (VerifyVramReleasedAsync)、`L530 StopNow 后的 _stopRequested=false`
- **类型**：可维护性
- **观察**：VerifyVramReleasedAsync 已有 try-catch 并 Log，OK。StopNow 的 `_stopRequested=false` 在 `_server.Stop()` 后立即执行——若 Stop 抛异常，`_stopRequested` 不会被重置，形成死锁（所有后续请求被 503 拦截，直到下次唤醒清除）。
- **代码片段**：

```csharp
public void StopNow()
{
    _stopRequested = true;
    _graceWakeEvent.Set();
    Log?.Invoke("正在停止 llama-server…");
    SetPhase(Phase.Standby);
    RaiseStatus(...);
    _server.Stop();              // ← 若此处抛异常
    _stopRequested = false;      // ← 此句不会执行 → 后续所有请求 503 死锁
}
```

**修复建议**：把 `_stopRequested = false` 放到 try-finally 中，确保任何情况下都被重置。
