## High 严重度

### [High] SlotPanelView.RefreshSlotMgmtGrid 行/索引无界增长 + 陈旧引用

- **文件行号**: `SlotPanelView.cs:113-139`
- **类型**: 控件无界增长 + 字典陈旧引用
- **触发**: 槽位生命周期（绑定/解绑）变更，RefreshBindings 被多次调用；绑定被移除后旧行仍留在表格中；绑定被移除后再新增，旧索引失效但残留
- **后果**: 
  1. DataGridViewRow 只增不减 → 槽位频繁变更时行数无界膨胀（GDI 句柄/控件对象缓慢泄漏）
  2. `_slotMgmtRowIdx` 中残留已解绑 key → 后续 RefreshSlotMgmtGrid 时 TryGetValue 命中陈旧 idx，覆盖正确行数据或越界
  3. 中间行被删除后 idx 错位 → 所有后续 key 映射到错误行
- **证据链**:
  - 调用点 `RefreshBindings()` (L77-85) 每次槽位绑定变更触发
  - 当 `bindings` 中不再有某个已存在的 key → 函数体中没有任何删除 DataGridViewRow 或清理 `_slotMgmtRowIdx` 的分支
  - 唯一清理路径是 `bindings == null` 时全量 Clear，但正常解绑不会传 null
- **代码片段**:
  ```csharp
  private void RefreshSlotMgmtGrid()
  {
      var bindings = _scheduler.GetSlotBindings();
      if (bindings == null)
      {
          _gridSlotMgmt.Rows.Clear();
          _slotMgmtRowIdx.Clear();
          return;
      }
      // ❌ 没有清除 _slotMgmtRowIdx 中不存在于 bindings 的旧 key
      // ❌ 没有删除 _gridSlotMgmt.Rows 中已解绑的旧行
      foreach (var (key, ...) in bindings)
      {
          int idx;
          if (!_slotMgmtRowIdx.TryGetValue(key, out idx))
          {
              idx = _gridSlotMgmt.Rows.Add();  // 只增不减
              _slotMgmtRowIdx[key] = idx;
          }
          // ... 只更新 value，不删除
      }
  }
  ```

## Medium 严重度

### [Medium] BuildPage RowStyles/ColumnStyles 只增不减（重复调用风险）

- **文件行号**: 
  - `StatusPanelView.cs:191-195`
  - `StatsPanelView.cs:72-75`
  - `MonitorPanelView.cs:69-70`
  - `PerfMonitorView.cs:67-213`
- **类型**: 集合只增不减
- **触发**: 任何原因导致 BuildPage() 被二次调用（MainForm 重建面板、Tab 重建等）
- **后果**: TableLayoutPanel 的 RowStyles/ColumnStyles 集合重复添加，行高/列宽错乱；Controls 集合也重复添加同引用控件抛 ArgumentException
- **代码片段（StatusPanelView 示例）**:
  ```csharp
  public Control BuildPage(...)
  {
      var grid = new TableLayoutPanel { ... };
      // ...
      for (int i = 0; i < cards.Length; i++)
      {
          grid.RowStyles.Add(new RowStyle(...)); // 无检查直接 Add
          grid.Controls.Add(cards[i], 0, i);
      }
      // ❌ 没有 RowStyles.Clear() 或 RowCount=0 的防御
  }
  ```
- **备注**: 当前调用路径只 BuildPage 一次，实际低风险；但 MonitorPanelView.UpdatePropsCard 已做了 RowStyles.Clear + RowCount=0 防御，BuildPage 作为公开 API 应保持一致的幂等性。

### [Medium] MonitorPanelView.Refresh() async void + Interlocked 防重入窗口竞态

- **文件行号**: `MonitorPanelView.cs:190-245`
- **类型**: async void + 防重入竞态
- **触发**: 用户快速连续点击「手动刷新」按钮（或其他触发 Refresh 的入口）
- **后果**: 
  1. `Interlocked.Exchange(ref _metricsBusy, 1)` 返回 1 时直接 return → 第二次刷新被静默丢弃（无任何提示），用户不知道刷新被合并
  2. `await _monitorCollector.CaptureSnapshotAsync()` 期间 UI 线程空闲，用户再次点击 → 因为 _metricsBusy 已为 1，新请求被丢弃 → 这是期望行为
  3. 但若第一个 Refresh 的 await 前后 _metricsBusy 被意外清零（比如 finally 在异常路径之外），会有并发风险
- **代码片段**:
  ```csharp
  public new async void Refresh()
  {
      if (Interlocked.Exchange(ref _metricsBusy, 1) == 1) return;  // 防重入 OK，但 silent drop
      try
      {
          // ... 同步采集
          await _monitorCollector.CaptureSnapshotAsync();  // await 点
          // ... 更新 UI
      }
      catch (Exception ex) { _appendLog?.Invoke(...); }
      finally { Interlocked.Exchange(ref _metricsBusy, 0); }
  }
  ```
- **备注**: async void 用于按钮 Click 事件处理器是可接受的模式（try-catch 已覆盖），Interlocked 防重入实现正确。"丢弃无提示" 属于 UX 问题而非 crash 风险。

## Low 严重度

### [Low] MonitorPanelView.Refresh 使用 `new` 关键字隐藏 Control.Refresh

- **文件行号**: `MonitorPanelView.cs:190`
- **类型**: 方法隐藏（Method Hiding）
- **代码片段**:
  ```csharp
  public new async void Refresh()
  ```
- **风险**: 如果外部代码写 `((Control)_this).Refresh()`，会调用基类的 `Control.Refresh()`（强制重绘）而非本方法（采集数据）。当前代码中只有 `_btnRefreshRes.Click += (_, _) => Refresh()` 这一处调用，使用的是编译期类型 `MonitorPanelView`，所以没问题。但 `new` 关键字本身是代码异味。

### [Low] SlotPanelView.RefreshSlotMgmtGrid 清理路径缺失与 RefreshSlotGrid 不对称

- **文件行号**: `SlotPanelView.cs:104` vs `SlotPanelView.cs:113`
- **类型**: 风格/对称性
- **代码片段**:
  ```csharp
  // RefreshSlotGrid (L95): bindings 为 null → Rows.Clear + return；bindings.Count == 0 → Rows.Clear → return
  // RefreshSlotMgmtGrid (L113): bindings 为 null → Rows.Clear + _slotMgmtRowIdx.Clear + return
  // ❌ 缺少 bindings.Count == 0 时的 _slotMgmtRowIdx.Clear() 清理
  ```

- **影响**: 当最后一个绑定被移除（bindings.Count == 0 而非 bindings == null），`_slotMgmtRowIdx` 中最后一条 key 残留；虽然不影响正确性，但与 RefreshSlotGrid 的逻辑不对称。

### [Low] PerfMonitorView.OnTick 内 CheckAlarms 每次构造新数组

- **文件行号**: `PerfMonitorView.cs:321-327`
- **类型**: 性能微优化
- **代码片段**:
  ```csharp
  private void CheckAlarms()
  {
      var pts = _sampler.Series.Last(AlarmWindowPoints); // 每次构造新 PerfPoint[] 切片
      if (pts.Length < 2) return;
  ```

## Observation 观察与防御建议

### [Observation] StatusPanelView.RefreshInFlightTasks 使用 DisposeChildren 但未考虑空集合场景

- **文件行号**: `StatusPanelView.cs:253-266`
- **说明**: `DisposeChildren()` 扩展方法已正确调用（`ControlExtensions.cs` 已提供），Label 创建用的 Font 来自 `UiTheme.GetFont`（进程级共享缓存），不会泄漏。当前实现正确。

### [Observation] PerfTrendChart Font 提升为实例字段 + Dispose 重写

- **文件行号**: `PerfTrendChart.cs:32-57`
- **说明**: 5 个 Font 在构造期创建、Dispose(bool disposing) 中释放，彻底消除了 OnPaint 每次 new Font 的 GDI 句柄泄漏。OnPaint 中 Pen/Brush 也都使用 `using var` 自动释放。这是本模块中资源治理最完善的文件。

- **文件行号**: `MonitorPanelView.cs:383-386, 403-406`
- **说明**: 两处调用点都做了 `DisposeChildren()` + `RowStyles.Clear()` + `RowCount = 0`，是 P1-1 审计修复的成果。但 BuildPage (L69-70) 作为初始化路径，应保持相同的防御性编程风格。

### [Observation] StatsPanelView 跨线程模式正确

- **文件行号**: `StatsPanelView.cs:104-152`
- **说明**: `OnRoundUpdated` / `OnRoundRemoved` / `OnSessionReset` 三个事件处理器都正确使用 `_uiReady()` guard + `_invokeOnUi()` 切回 UI 线程，无 BeginInvoke/Invoke 混用问题。DataGridViewRow 的添加/删除也走 UI 线程串行执行。
