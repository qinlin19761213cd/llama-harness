# g6 组审计发现：日志与配置模型（LogFile / LogPipeline / AppConfig / AppPaths / TokenGuard）

> 审计范围：LogFile.cs / LogPipeline.cs / AppConfig.cs / AppPaths.cs / TokenGuard.cs

## 发现清单

- [低] AppPaths.cs:103 — BackendExeCandidates 硬编码绝对路径 `C:\llama.cpp\build\bin\Release\llama-server.exe`
  - 触发条件：本机未安装 llama-server 且用户目录无副本时，LlamaFinder 搜索该候选
  - 代码路径：BackendExeCandidates() 返回 3 个候选，其一为硬编码 C: 盘路径（:103）；与项目"路径集中管理"目标一致但路径本身仍是魔法值
  - 破坏后果：换机/换盘符后该候选恒无效（LlamaFinder 有后续搜索兜底，无行为错误）；属 O-11 魔法值治理的遗漏残余
  - 修复：删除硬编码盘符候选，或改为可配置（AppConfig.ExtraArgs 或环境变量）；保留 BaseDir 与 userProfile 相对候选即可

- [低] LogPipeline.cs:324-341 — _wake 信号从未被 Enqueue 触发（写线程实际 150ms 轮询）
  - 触发条件：日志持续入队时（正常生产路径）
  - 代码路径：Enqueue（:324）只 lock + TryEnqueue，无 `_wake.Set()`；WriterLoop 的 `_wake.Wait(150ms)`（:341）实际只靠超时 tick 唤醒；_wake.Set() 仅在 Shutdown（:451）
  - 破坏后果：日志入队后最长 150ms 才被写出（可接受延迟）；空队列时写线程每 150ms 空醒来一次（6.7 次/秒空转，几乎零成本）。行为正确，但"数据信号"机制形同虚设，与注释（:335"等数据信号或 150ms tick"）不符
  - 修复：Enqueue 成功入队后 `_wake.Set()`，使高吞吐场景延迟降到毫秒级、空队列零轮询

- [观察] LogPipeline.cs:444-464 — Shutdown 超时路径后 WriteDirectSafe 与写线程并发写同一 StreamWriter
  - 触发条件：关闭瞬间写线程卡在 IO（磁盘满/占用），Join(3s) 超时
  - 代码路径：Shutdown 超时分支（:460-463）不 Dispose writer（防与写线程竞争句柄），但随后 WriteDirectSafe 直接写 _mainWriter——主线程与可能仍在写的写线程并发访问同一 StreamWriter（无锁）
  - 破坏后果：关闭瞬间可能产生交错写入/未定义行为（尽力而为路径，进程即将退出）；设计注释已说明权衡（daemon 线程随进程退出）
  - 建议：超时分支改为只计数不入队写日志（避免并发写），或对该次写加锁

- [观察] LogFile.cs:18-21/:100-102 — _recent 环形缓冲容量 = ContextLines(10)，/__status__ recent_logs 仅最近 10 条
  - 触发条件：通过 /__status__ 查询 recent_logs 诊断时
  - 代码路径：_recent 复用 WarnContextLines=10 常量（:21），Append 后 while Count>10 Dequeue（:101）
  - 破坏后果：远程诊断只能看到最近 10 条日志（启动早期/崩溃前关键日志可能已被挤掉）；与"诊断盲区消除"目标存在差距
  - 建议：recent 容量独立常量（如 50-200 条）

- [低] AppConfig.cs:162-184 vs MainForm.Config.cs:106-107 — 两套数值兜底语义并存（Sanitize 回默认 vs ReadInt clamp 区间）
  - 触发条件：配置越界值进入 Load/导入（Sanitize 路径）或 UI 编辑（ReadInt 路径）
  - 代码路径：Sanitize 对 Port<1 回 8080（:164）；ReadInt 对 Port clamp 到 [1,65534]（MainForm.Ui.cs:11 常量 + Config.cs:106）
  - 破坏后果：两条路径对同一越界值的处理结果不同（Load 回默认、UI clamp）；当前导入路径先 Sanitize 后 ApplyConfigToUi（clamp 覆盖），行为一致无 bug，但语义双轨增加维护认知负担
  - 建议：统一为单一 Sanitize 入口（UI 写入前也走 Sanitize 或明确文档化两套语义）

- [低] TokenGuard.cs:302 — EstimateTokensByChars `ch >= 0x20000` 死分支（char 为 16 位，恒 false）
  - 触发条件：代码维护
  - 代码路径：:302 `(ch >= 0x20000 && ch <= 0x2FFFF)` 对 UTF-16 char 永远不成立（0x20000 超出 char 范围）；surrogate pair 已由 :303 high surrogate 分支覆盖
  - 破坏后果：无行为影响，死代码
  - 修复：删除死分支
