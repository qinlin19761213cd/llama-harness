## 发现清单

- [中] PerfAnalyzer.cs:102-160 — 告警状态机（冷却/升级/恢复事件）为死代码，AlarmRaised/AlarmRecovered 永不触发
  - 触发条件：任何告警产生路径（实时窗口 EvaluatePoints / 请求级 EvaluateTiming）
  - 代码路径：TryRaiseAlarm（:125）/ OnRecover（:150）/ _lastAlarmUtc（:108）/ _curLevel（:109）/ AlarmRaised（:102）/ AlarmRecovered（:104）——经全库 Grep 核实，**除定义与声明外无任何调用点**；EvaluatePoints（:206/:216）与 EvaluateTiming（:242-244）直接 `alarms.Add(MakeAlarm(...))`，不走 TryRaiseAlarm
  - 破坏后果：①60s 冷却、Warn→Crit 升级、告警恢复（Recovered）通知这三个设计能力全部未接入；②订阅 AlarmRecovered 的 UI/日志（若存在）永远不会收到"恢复正常"事件——持续告警只能靠阈值下方新触发覆盖，无法通知恢复；③TryRaiseAlarm/OnRecover/_curLevel/_lastAlarmUtc 为无效代码（编译器不警告但语义断裂）
  - 修复：EvaluatePoints/EvaluateTiming 内按 metric 接入 TryRaiseAlarm（冷却）与 OnRecover（越界→未越界迁移）；或删除死代码并在文档注明冷却/恢复由 UI 层（PerfMonitorView.AddAlarm 冷却）承担

- [中] PerfSampler.cs:151-155 vs :46-52 — 采样点 Ts 使用 DateTime.Now，D3 单调时钟合成（NowMonotonic）未生效
  - 触发条件：系统时钟回拨 / 夏令时切换 / NTP 校准时（用户桌面 NTP 同步常见）
  - 代码路径：OnTick 组装 PerfPoint 时 `Ts = DateTime.Now`（:153）；D3 修复定义的 NowMonotonic()（:51-52，Stopwatch 偏移合成）在本类内无调用（已核实）
  - 破坏后果：相邻采样点 Ts 可能倒挂（后采的点 Ts 更早）→ PerfTrendChart 时间轴错乱、PerfAnalyzer 连续窗口扫描顺序异常、perf.log 时间戳回退；D3 修复（针对 DateTime.Now 回拨）实际未落地到采样点
  - 修复：`:153` 改 `Ts = NowMonotonic()`
  - 注：RequestTimingTracker.Complete 的 `Ts = DateTime.Now`（:83）同类但为请求事件非时间序列，影响面小，可一并评估

- [低] MetricKeys.cs:9-86 vs PerfAnalyzer.cs:164-177 — 指标键"唯一权威"注册表与实际支持集不一致（双轨）
  - 触发条件：未来按注册表键配置 perf_thresholds 或新代码用 MetricKeys 常量取值
  - 代码路径：MetricKeys 注册 GenTps="gen_tps" / PromptEvalTps="prompt_eval_tps" / Vram="vram"（:41-45/:65）并声明"唯一权威、禁止变体"（:4-6）；PerfAnalyzer.ValueOf 实际只认旧短键 "tg_tps"/"pp_tps"/"vram_mb"（:170-171）；PerfThresholdRule.Defaults 也用旧短键（:33-34）
  - 破坏后果：当前默认规则恰好用旧键故行为正确；但若用户按注册表键（文档宣称的口径）配置阈值，ValueOf 返回 null → 告警静默失效且无任何提示；注册表声明与实现矛盾，维护者无法判断权威口径
  - 修复：ValueOf 补注册表键映射（或 MetricKeys 删除"唯一权威"声明改为兼容层）；加测试断言 MetricKeys.All 每键在 ValueOf 有映射

- [低] PerfAnalyzer.cs:292-356/:363-417 — D6 复查：ParsePerfLog / ParseSessions 仍无最小样本数下限
  - 触发条件：perf.log 刚启动（仅几条记录）时做离线分析
  - 代码路径：ParsePerfLog 对任意行数直接出摘要（TotalLines>0 即有效）；ParseSessions 单条 cpp/timing 行即出 MinTgTps/AvgTotalMs
  - 破坏后果：样本不足时 MinTgTps / AvgTotalMs / 会话对比结论基于 1-2 个点，误导性高；UI 无样本数门限提示
  - 修复：摘要模型加 MinSamples 门限（如各指标非空样本 >=3 才出统计），不足时 UI 显示"样本不足"

- [低] PerfSampler.cs:133/:182-260 — SampleSlowAsync fire-and-forget（`_ = SampleSlowAsync()`）无调用方级异常兜底
  - 触发条件：慢采样任务异常路径（内部各段已有 try/catch + finally Release）
  - 代码路径：OnTick `_ = SampleSlowAsync()`（:133）；方法体各段 catch + finally 释放信号量（:256-259）
  - 破坏后果：内部已全覆盖，实际无逃逸路径；但该模式脆弱——未来在 WaitAsync(0) 前插入 await 点会失去保护（Task 未观察异常 → 线程池崩溃）

- [观察] PerfSampler.cs:242-247 — tg_tps/pp_tps 数据源兼容性：/metrics 缺失时回退 /slots 均值，prefill 期 tg=0 可能触发"生成吞吐骤降"误报
  - 触发条件：负载期（Inflight>0）后端处于 prefill 阶段（SlotsProcessing>0 但生成未开始），tg_tps=0
  - 代码路径：IsIdlePoint 只按 Inflight/SlotsProcessing 门控（:231-232），prefill 期两点均非空 → 不跳过 → tg_tps=0 持续 MinDurationSeconds 触发 Below 告警
  - 破坏后果：用户曾反馈"生成吞吐一直都是 0 超过阈值"——与此链路相关（数据源 0 值 + 门控未覆盖 prefill 期）；真实负载下 prefill 通常 < 数秒，30s 持续 0 多为后端未就绪/接口异常场景
  - 建议：tg_tps=0 且 SlotsProcessing>0 时结合 tokens_cached 是否增长判断（prefill 中），或将 0 值视为未知（null）跳过告警
