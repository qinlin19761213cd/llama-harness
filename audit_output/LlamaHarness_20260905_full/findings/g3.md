# 审计发现 - g3 后端契约与进程

覆盖：IBackendClient + BackendClientFactory + LlamaServerClient + LlamaFinder + LlamaServerProcess + LlamaStatsParser + OutputContinuer + CpuAffinity + SystemMetrics + LlamaCppMonitor（10 文件）
基线：git 93d5432（v2.26.4）

## [观察] OutputContinuer.cs:385-389 — PipeOneRoundAsync finally 无条件 outResp.Close() 与续接语义潜在冲突（建议优先验证）
- 描述: finally 块对**所有** return 路径执行 `outResp.Close()`（含 Truncated 续接分支），与 AH-4 注释"超时/异常路径下确保关闭响应"的意图不符。截断续接（Truncated）需继续用同一 outResp 写下一轮 SSE，Close 后继续写依赖 .NET 实现细节（当前实测续接功能正常，未复现异常——但行为未在注释/契约中定义）。
- 触发路径: 任何 finish_reason=length 的截断续接（多轮写同一 outResp）。
- 后果: 若目标 .NET 版本 Close 后 OutputStream 写抛 ObjectDisposedException，续接输出静默丢失且难排查（上层 catch 记录"响应管道异常"）。
- 建议: 改为仅 Aborted/异常路径 Close；Normal/Truncated 由调用方（PipeLoop 末轮后）统一关闭；或至少在注释中明确"Close 后仍可写"的契约并加防护。

## [低] LlamaCppMonitor.cs:111-113 — 3 个独立 CTS 未 Dispose
- 描述: slotsCts/propsCts/metricsCts 创建后仅依赖 GC；CancelAfter(8s) 计时器在 GC 前存活。手动触发低频（点击采集），泄漏量微小，但违背 CTS 使用规范（P0-H-05 修复了共享 CTS 却漏了独立 CTS 的释放）。
- 建议: 三个 CTS 放入 using var 或 try/finally Dispose。

## [低] LlamaServerClient.cs:68 — SendAsync 每次调用创建不可取消的 60s Task.Delay
- 描述: `Task.Delay(60s, CancellationToken.None)` 每请求一个；请求 5s 完成时该 delay task 仍挂 55s（引用丢弃后靠 GC 回收），高并发下短暂累积活动定时器。
- 建议: 复用 linkedCts.Token 或改用 CancellationTokenSource.CancelAfter 的单一 CTS 方案。

## [低] LlamaFinder.cs:167-177 — ExtraArgs 白名单按字符静默删除不允许字符
- 描述: 白名单过滤是"删除非法字符"而非"拒绝整个参数"：如用户写 `--chat-template "path with space"`，引号被删 → 语义变成 3 个 token；`--flag=1&2` 中 `&` 被删 → 静默改值。注入防护有效，但静默改变用户配置意图。
- 建议: 遇到非法字符时拒绝该参数并告警（如 `--extra-args-rejected`），而非静默删字符；或允许 `"` 并做双引号转义（与 EscapeArg 一致）。

## [低] LlamaStatsParser.cs — RoundStats 引用对象跨线程无锁读
- 描述: Feed（进程输出线程）在锁内修改 round 属性，RoundUpdated 事件锁外触发；UI 线程读取 round 时可能读到部分更新的中间态（double/long 属性赋值原子，整体不一致概率低）。
- 建议: 事件参数传递不可变快照副本，或 UI 侧读取后做一致性校验。

## [低] LlamaServerClient.cs:172-185 — GetJsonAsync 返回 JsonDocument 无所有权契约
- 描述: 返回的 JsonDocument 需调用方 using 释放，但接口/注释未声明所有权；漏 Dispose 时泄漏内存池（低频轮询可接受，但契约不明确易误用）。
- 建议: 注释明确"调用方负责 Dispose"或改为返回解析后的强类型/文本。

## [低] LlamaCppMonitor.cs:28-39 — LlamaSlotInfo 属性命名违反 C# 规范
- 描述: id/state_name/tokens_cached 等小写下划线命名（JSON 直映），与项目其余类型 PascalCase 不一致（System.Text.Json 可用 JsonPropertyName 映射）。
- 建议: 属性改 PascalCase + [JsonPropertyName] 映射。

## [低] LlamaServerProcess.cs:51-58 — Start 每次重建输出事件订阅
- 描述: OutputDataReceived/ErrorDataReceived 每次 Start 新订阅 lambda（旧 proc Dispose 后事件源失效，无实际泄漏），但重复订阅模式可读性差。
- 建议: 保持现状（行为正确）或改为一次性订阅 + 局部转发。

## [观察] BackendClientFactory.cs（B4 遗留复查）— 仍无 BackendKind 后端类型抽象
- 描述: 工厂仅 Create(baseUrl, handler) 硬编码返回 LlamaServerClient；注释提及"未来按运行时端口/协议分发"，但无枚举/契约标识。上轮评审遗留 B4 未修，当前单后端场景无功能影响。
- 建议: 未来接入第二后端（vLLM）时引入 BackendKind 枚举 + 工厂分发；当前可先记入技术债。

## [观察] SystemMetrics.cs:88-93 — GetVramUsedMbAsync 静态 vs GetVramTextAsync 实例方法不一致
- 描述: 同类显存查询一个 static 一个实例（依赖 _vram 缓存与否的差异），风格不统一。
- 建议: 统一为实例方法或静态（当前无行为问题）。

## [低] LlamaStatsParser.cs:54 — print_timing 正则 task 归组依赖 id 行前缀
- 描述: TaskIdRe 要求行含 "print_timing:" 前缀；llama.cpp 新版本若改行格式（如去掉 id/task 段）会导致归组失效（解析静默降级，UI 无感知）。当前两种实测格式均已兼容。
- 建议: 保持现状；升级 llama.cpp 时注意回归验证。
