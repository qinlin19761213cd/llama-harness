## [中] SmartScheduler.Lifecycle.cs:202 — 前缀哈希/漂移差异字典未随唤醒清空（无界增长）
- 描述: InitRuntimeAssemblies 仅 Clear `_servedKeysThisRun/_savedKeysThisRun/_freshSnapshotKeys` 三个集合；`_prefixHashes`（SmartScheduler.cs:133）与 `_lastDriftDiff`（:134）未在唤醒时清空。unknown_ 前缀 key 携带随机 UUID（每新会话新 key），每次请求都会向 `_prefixHashes` 写入一条（Gateway.cs:368/371），长期运行（多次唤醒 + 大量 unknown 会话）字典条目持续累积。
- 根因: 前 3 个集合语义是"唤醒周期内标记"，后 2 个集合语义上是"会话级基线"，但实现未区分生命周期。
- 建议: 唤醒时（InitRuntimeAssemblies）一并 Clear `_prefixHashes`/`_lastDriftDiff`；或按 key 数设上限（如 512 条 FIFO 淘汰）。

## [低] SmartScheduler.Http.cs:255 — async 方法内同步阻塞调用
- 描述: HandleHealth 内 `RequestProcessor.WriteJsonAsync(ctx, 200, json).GetAwaiter().GetResult()`。AcceptLoop 运行于线程池（Task.Run 启动），无 UI SynchronizationContext，无死锁风险，但违反 async 最佳实践、阻塞线程。
- 建议: HandleHealth 改 async Task<bool>，直接 await。

## [低] SmartScheduler.Http.cs:391/426 — rtId 跨线程读写竞态
- 描述: `rtId` 局部变量在 Task.Run 闭包内赋值（:391），外层 catch（:426）读取。正常完成路径有 Task 完成屏障，安全；看门狗超时路径 handlerTask 仍在后台执行时，外层读到的 rtId 可能为 null/旧值，仅影响性能打点完整性。
- 建议: rtId 改为 volatile 字段或 Task.Run 返回 rtId。

## [低] SmartScheduler.Pipeline.cs:465 — dump 截断后字节数标注失真
- 描述: `bodyStr.Substring(0, DumpBodyMaxLength) + "...(truncated, total {GetByteCount(bodyStr)} bytes)"` —— 截断后 bodyStr 已是 2000 字符，GetByteCount 返回的是截断后字节数而非原始请求体字节数，日志标注 "total" 与事实不符。
- 建议: 截断前先记录原始 bodyBytes.Length。

## [低] SmartScheduler.Lifecycle.cs:513-514 — SetPhase 注释与实际逻辑顺序不符
- 描述: 注释写"先写入再比较旧值，避免 TOCTOU 窗口"，实际代码是 `oldPhase = Volatile.Read(...)` → 比较 → `Volatile.Write(...)`（先读后比再写）。注释与实现矛盾，误导维护者。
- 建议: 修正注释或按注释意图调整实现（当前实现本身无竞态问题）。

## [低] SmartScheduler.Lifecycle.cs:212/246 — 就绪等待 5 分钟魔法值未提常量
- 描述: `deadline = DateTime.Now + TimeSpan.FromMinutes(5)` 与 `throw new TimeoutException("等待 llama-server 就绪超时（5 分钟）")` 硬编码 5 分钟，未提常量（同文件其它超时均已常量化）。

## [低] SmartScheduler.Gateway.cs:437-444 — StripThinkingTags 嵌套标签残留孤立闭标签
- 描述: 正则 `<thinking>.*?</thinking>`（非贪婪）对嵌套输入 `<thinking>A<thinking>B</thinking>C</thinking>` 首次匹配剥掉 `A<thinking>B</thinking>` 段，剩余 `C</thinking>` 孤立闭标签无法被 openRe 兜底清除。注释声称"嵌套的最外层闭合对一次剥到最外对"与实际正则行为不符。
- 建议: 用平衡匹配或先剥最内层；或接受残余（边缘场景）并修正注释。

## [低] RequestProcessor.cs:230-235 — EnsureStreamTrue 字符串降级插入位置风险
- 描述: DOM 解析失败时在"最后一个 `}`"前注入 `"stream":true`，若请求体含 tools 数组（数组内 `}` 在 messages 后），注入位置可能在数组元素内/末尾而非顶层。仅 DOM 失败路径触发，且改写后经 JSON 校验（Gateway.cs:128-138）兜底拒绝损坏数据。
- 建议: 保持现状（有校验兜底），或改用首层 `{` 后注入。

## [低] ThinkingMode.cs:111-124 — 矛盾思考指令按 if 顺序覆盖
- 描述: 同一消息同时含"开启思考模式"与"关闭思考模式"时，按 hitOn→hitOff 顺序执行，最终结果取决于代码顺序（Off 覆盖 XHigh）；语义不明确但无崩溃风险。
- 建议: 命中多个互斥指令时以最后出现者为准或记录警告。

## [观察] SmartScheduler.Http.cs:398-412 — 看门狗超时后 handlerTask 孤儿执行
- 描述: 整体 300s 超时后客户端已收 504，但 handlerTask 不取消继续后台跑（Pipeline 各阶段 CTS 兜底）。超时即放弃响应，重负载下可能积累孤儿任务。
- 建议: 超时路径尝试 handlerCts 联动传递取消；或在文档中明确"超时后后台继续直至自身 CTS"的语义。
