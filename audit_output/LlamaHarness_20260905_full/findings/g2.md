# 审计发现 - g2 KV 与槽位

覆盖：KvCacheManager + SlotAffinity + AffinityRule + AffinityRuleMatcher + RestoreStats（5 文件）
基线：git 93d5432（v2.26.4）

## [中] SlotAffinity.cs — 绑定表无界增长，StaleBindingDays 常量定义了但从未用于清理
- 描述: `_bindings` 字典仅在建新绑定（TryAllocateLocked）、驱逐、启动裁剪时变化，**从不按时间淘汰**。`StaleBindingDays = 30`（:19）只在 Load() 时用于无效时间戳兜底（:431 `dt = DateTime.Now.AddDays(-StaleBindingDays)`），无任何"30 天未活跃 → 移除绑定"的清理逻辑。dsh_rule_/unknown_ 前缀 key 携带会话 UUID，每次新会话 +1 条绑定，slot_bindings.json 持续膨胀。
- 触发路径: 长期运行（多次唤醒）+ 带会话 ID 的亲和 key（如 dsh_rule_{uuid}）。
- 后果: 内存与持久化文件缓慢无界增长；unknown 有 16 条上限，正式规则 key 无上限。
- 建议: 启动/Load 时按 LastActive 清理超过 StaleBindingDays 的绑定（保留 Preemptive=true 的），或给 _bindings 设条目上限。

## [低] SlotAffinity.cs:286 — Save() 文件 IO 在 _gate 锁内
- 描述: TryAllocateLocked 建新绑定路径在 `lock(_gate)` 内调用 Save()（File.WriteAllText + File.Move 同步 IO）。新 key 首次请求触发写盘期间，所有路由/驱逐/快照操作阻塞于同一把锁（毫秒级）。
- 建议: 锁内更新内存、标记 dirty，锁外写盘（同 KvCacheManager.RecordSave 的 AH-13 模式）。

## [低] SlotAffinity.cs:474-479 — TryGetHeader 死代码
- 描述: `TryGetHeader` 恒定返回 true（注释明示"死防御删除"后保留），且全仓库无调用方（已 grep 确认仅定义处 1 处）。
- 建议: 删除该方法。

## [低] SlotAffinity.cs:421 — 绑定文件双重 JSON 解析
- 描述: Load() 先 `JsonDocument.Parse(File.ReadAllText(...))` 再 `JsonNode.Parse(doc.RootElement.GetRawText())`，同一文档解析两遍。
- 建议: 直接 JsonNode.Parse 原始文本即可。

## [低] KvCacheManager.cs:198 — TrimToQuota fire-and-forget 无并发保护
- 描述: DoSaveAsync finally 内 `_ = Task.Run(() => TrimToQuota())`，注释称"单线程执行"；实际每次 save 完成都新起一个 Task，多个 save 同时完成时并发执行 TrimToQuota（无互斥）。删除操作幂等 + _index 有 lock 保护，实际风险低，但注释与实现不符。
- 建议: 加 Interlocked 或信号量防重入（如 `if (Interlocked.Exchange(ref _trimming, 1) == 1) return;`）。

## [低] KvCacheManager.cs:586-587 — Sanitize 128 字节截断可致 key 撞名
- 描述: 超长 key 按 UTF-8 字节 128 截断，两个不同但前 128 字节相同的 key 会得到相同文件名，快照互相覆盖（元数据 session_id 可区分但 .bin 被覆盖）。
- 建议: 截断时追加内容哈希后缀（如前 112 字节 + hash8），或保持现状（实际 key 短，触发概率极低）。

## [观察] KvCacheManager.cs:94-109 — DeleteCache 不等待在途 save
- 描述: ClearAllAsync 有 AH-10 在途 save 等待，但单 key DeleteCache 直接删文件+索引；若同一 key 有在途 save（如后台快照），save 完成后文件"复活"而索引条目已被删（孤儿 .bin，下轮 TrimToQuota 清理）。
- 建议: 删除前等待同 key 在途 save（与 RestoreAsync 的等待模式对齐）。

## [低] RestoreStats.cs — _byKey 字典无界增长
- 描述: `_byKey[p.Key] = ks`（:180-181）每新 key +1，持久化 by_key 数组同步累积；unknown 会话 UUID key 长期运行持续增长（无上限、无淘汰）。
- 建议: 与 SlotAffinity 同类——按 key 数上限（如 256）或 LastActive 淘汰，或 unknown_ 前缀聚合统计。

## [低] RestoreStats.cs:223/227 — JudgeResult 对象构建两次
- 描述: OnPromptEval 在 lock 内为 LastJudgeResult 构建一次，return 前再构建一次完全相同对象（10 参数 record），冗余分配。
- 建议: 构建一次，赋值与返回复用同一实例。

## [观察] RestoreStats.cs:148-152 — FIFO TTL 60s 丢弃慢任务判定
- 描述: 入队到 prompt eval 行到达间隔 > 60s 时条目被丢弃（判定丢失）；长 prefill 排队场景会低估命中统计。属设计权衡（防错位），注释已说明。
- 建议: 保持现状；如统计完整性重要可将 TTL 提到 120s。

## [低] AffinityRuleMatcher.cs:74-76 — unknown key 哈希 48bit 碰撞窗口
- 描述: UA → SHA256 前 12 hex（48bit）→ unknown_{hash}；不同 UA 碰撞概率低（生日悖论 ~几万条级别），且碰撞后果仅是两应用共享绑定/KV（非安全问题）。
- 建议: 保持现状（已在注释说明防护意图）。
